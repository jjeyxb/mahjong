# 專題方向的轉折與現有成果

> 記錄期間:2026-07-26 ~ 2026-07-29
> 這份文件的用途是保存**決策過程**與**已經做完但不再使用的量測成果**。
> 專案現況與使用說明看 [README](../README.md),這裡只講「為什麼變成現在這樣」。

---

## 一、原始構想

最初的設計是一條單線:

```
螢幕擷取 → CV 辨識整個牌桌 → tracker 拼成事件流 → MJAI → Mortal → HUD 建議
```

封包解析(WebSocket / liqi protobuf)只當 **Ground Truth**,不參與線上決策,
用途是替 CV 產生標註資料集、並量化 CV 的準確率。

論述點是:「電腦視覺能不能可靠地重建一個即時對局的完整狀態」,並用 GT 把
「準確率」從一句宣稱變成可重現的實驗數據。

這個構想在 M0–M2 都成立,而且 M2 做得比預期好(見第四節)。**問題出在 M3。**

## 二、CV 撞到的三道牆

### 牆 1:切牌訊號綁在可自訂的材質上

雀魂的牌有一圈橘色斜面,而且它是**無花紋的**,不像牌面有圖案會干擾。
所以 `vision/tiles/segment.py` 用它當切牌依據 —— 實測 14/14 張、誤差 ±1px,
還能用斜面方向區分暗手牌(斜面在上)與副露(斜面在下)。

但量下去發現:**手牌斜面 H=16,對手的蓋牌牌背也是 H=16 —— 是同一個材質。**
而牌背是玩家可以自訂的。也就是說整個切牌訊號建立在一個會被使用者換掉的東西上。

**這一牆後來確認可解。** 牌背由主視角玩家決定,同一場對局內四家統一,
所以只要開局時就地量一次(對面的暗手牌永遠是一整排牌背、位置固定、開局必定
存在),取其主色相當本場基準即可,不需要寫死。這比寫死更穩。

### 牆 2:立直橫放破壞牌河的網格假設

牌河是 6×3 的網格。3D 斜視角讓它在畫面上變成梯形(上家與下家的甚至是斜的),
所以我改用四個角 + 單應變換來切格 —— 平面矩形投影後必定仍是四邊形,四個角
就唯一決定全部 18 格,而且同一個變換反過來能把每格反扭回正矩形,四家共用
一套牌面模板。這部分實作完成、12 個測試通過、四家的角也標好了。

**但立直的橫放牌比較寬。** 那一列仍然是 6 張,卻不再是均勻的 6 等分,
均勻網格表示不了。沒有便宜的解法。

### 牆 3:校正在幀與幀之間會跳

這是最晚發現、也最嚴重的一個。

ROI 全部是相對 `table_rect` 正規化的,而 `table_rect` 由「從四邊往內剝除
整條同色帶狀區域」的啟發式在**每一幀**重新推導。拿一份 216 幀的錄影全跑一次:

```
216 幀 → 21 種不同的 table_rect
  2560x1430@(0,174)   108 幀  ← 正確的
  2560x1429@(0,174)    61 幀
  2560x1440@(0,174)    13 幀
  2460x1440@(75,174)    6 幀
  2302x1429@(5,174)     5 幀  ← 寬度少了 258 px
  2564x1692@(0,0)       4 幀  ← 完全沒剝掉瀏覽器工具列
  2560x1142@(0,174)     1 幀  ← 寬高比 2.24
  …(還有 14 種)
```

和了畫面、角色立繪、暗轉動畫都會破壞那個啟發式。`table_rect` 從 2560 變成
2302,**每個 ROI 就整體位移約 10%(≈100 px)** —— 比一張牌還寬。

矩形 ROI 看起來沒事,只是因為框大又剛好測在好的幀上;網格的格子只有一張牌
那麼大,同樣的誤差立刻現形。

> 這一牆**與牌河無關,只做手牌 CV 一樣會中**,所以仍然要修。
> 修法:校正只做一次然後鎖住(視窗尺寸沒變就不該重算),再加一道穩定性檢查
> (取前 N 幀的眾數、丟棄寬高比偏離太多的結果)。列在 M3 的第一項。

### 一個過程中的誤判,值得記下來

我一度認定「用 a3 標定的網格,套到另一份錄影就對不準」是個查不出原因的異常。
實際上是我拿錯了比較對象:`data/roi_ref/aligned/_align_test.png` 不是一張畫面,
而是那份錄影 216 幀 max-blend 疊出來的**合成圖**,不同時間點的牌全疊在一起。
拿網格去對它本來就不會準。

換成真實單幀重測,才浮出上面第三牆的真正原因。
**教訓:發現「異常」時先確認比較基準本身是什麼東西。**

## 三、為什麼是這三個功能

第二節那三牆讓 CV 的成本一路上升,於是重新檢視整個題目,問了兩件事:

**(a) 全牌桌 CV 真的值得繼續耗嗎?**

不值得。牌河 CV 的難度來自 3D 透視 + 立直橫放 + 遮擋,而它換來的東西 ——
完整對局狀態 —— **封包路徑已經 100% 拿得到了**(M2 實測 569 frame 全解析成功)。
用一條又難又不準的路去重建一條已經完美的路能給的資料,是把成本花在沒有回報
的地方。

**(b) 那跟 Akagi 的差異在哪?**

Akagi = 封包攔截 + 掛上 Mortal 公開權重。如果本專題也只是這樣,就沒有差異。
所以差異必須由**別的東西**承擔。

於是拆成三個獨立功能:

| # | 功能 | 狀態來源 | 差異化在哪 |
|---|---|---|---|
| 1 | 手牌 CV + 向聽計算 | CV(只需自己的手牌) | 不需要封包、不碰遊戲連線的輕量模式 |
| 2 | 麻將 AI 建議 | 封包(GT 那條路) | 與 Akagi 同級,是基礎能力不是賣點 |
| 3 | 打法風格微調權重 | 離線訓練 | **主要賣點**,見 README |

三者**互相解耦**:功能 1 只吃畫面、功能 2 只吃封包、功能 3 產出一份 `.pth`。
任何一個做不完都不會擋住其他兩個,UI 做好之前或之後都能補。

### 連帶消失的東西

- **tracker 層(原 M4)整層拿掉。** 它存在的唯一理由是把 CV 的逐幀觀察拼成
  事件流並做規則校驗。封包直接給事件,不需要拼,也不需要校驗。
- 原本「Observation 與 GameState 分離」那條設計原則沒有東西可以套用了 ——
  但它在 M2 仍然以另一種形式存在:擷取端只寫原始 frame,解析全在離線階段。

### 為什麼副露的內容不需要辨識

功能 1 要算的是**向聽數**,而向聽數只需要知道副露的**組數**,不需要知道副露
了什麼 —— 副露在計算上就是一組已完成的面子,內容不影響向聽。而組數可以直接
從手牌張數反推:`(13 - 手牌張數) / 3`。

唯一受影響的是**受入枚數**的精確度:不知道副露吃掉哪些牌,剩餘張數會略微
高估。這是次要問題,若要修可以從封包補,或在 UI 上標示為估計值。

## 四、已完成且仍然有效的成果

方向調整不影響 M0–M2,這些都還在。

### M1:擷取與校正(macOS 實機驗證)

| 項目 | 結果 |
|---|---|
| `CGWindowListCreateImage` 在 macOS 26 | 仍正常(雖自 macOS 14 起標記 deprecated) |
| 雀魂 Steam 版擷取 | 3024×1740 @ **60 fps**(16.7 ms/frame) |
| **視窗被遮擋時** | **仍可正確擷取** —— 抓的是視窗自身緩衝區,Overlay 可直接疊在遊戲上 |
| mss fallback | 只回傳邏輯解析度,像素少一半,確定僅作備援 |

過程中修掉的三個真實缺陷:

1. `cv2.cvtColor` 取代 numpy 跨步切片做 BGRA→BGR,輸出完全相同但快約 **50 倍**
   (0.16 ms vs 7.9 ms),擷取幀率從 47 fps 拉到 73 fps。
2. **圓角視窗破壞背景色推測** —— macOS 視窗四角是透明像素,premultiplied 後
   變純黑,亮色標題列的視窗會被誤判成「背景是黑的」。背景取樣改為排除四角。
3. **視窗比對假陽性** —— VS Code 開著檔名含「雀魂」的檔案時,標題命中且視窗
   比遊戲大,「取最大」的啟發式會選錯。改為加權評分:程式名 > 標題完全相符 >
   標題子字串。

### M2:封包 → MJAI(真實對局驗證)

**這一層現在是功能 2 的主幹,不再只是評測工具。**

- 協定定義自網頁版的 `liqi.json` 取得:**1318 個訊息、439 個 RPC、4625 個欄位**,
  全數成功轉成 Python protobuf 型別。
- 真實對局結果:**569 個 frame 100% 解析成功、242 個動作、249 個 MJAI 事件**,
  且 **242/242 全部需要 XOR 反混淆** —— 同時證實金鑰表與嘗試順序都正確。

過程中的幾個關鍵發現:

- **真實流量抓出一個合成測試抓不到的 bug。** 第一次錄真實對局時 242 個動作
  **一個都沒解析出來**,而當時 262 項測試全數通過。原因是 `ActionPrototype.name`
  在實際協定裡是**未限定的裸名**(`"ActionDiscardTile"`),不像外層 `Wrapper.name`
  是完整名。我照著自己的錯誤假設造測試資料,於是測試只證明了「實作符合我的
  理解」,證明不了「我的理解符合現實」。
- **「能解析」不等於「解對了」。** 6 位元組的 `ActionDiscardTile` 做 XOR 之後
  **照樣能被 protobuf「成功」解析**(所有位元組落進 unknown fields)。只靠
  try/except 選分支會拿到一個空動作。判準改為「有沒有解出任何已知欄位」。
- **和了的點數增減加總不是零**,是 1000 的倍數 —— 立直棒在 MJAI 記帳模型裡由
  `reach_accepted` 扣除、不進 `delta_scores`,但贏家收供託時會算進去。
- **錄製格式用 JPEG q95**:PNG 級別 1 寫入 127 ms 會直接掉幀,JPEG q95 只要
  9 ms,而對模板比對的影響只在小數第四位(1.000000 vs 0.999800),峰值位置相同。
- **畫面去重**:一場對局約 **80% 的幀沒有變化**,45 秒錄影從 378 MB 降到 119 MB。

### M3:已完成的部分

- **`vision/roi.py`** —— 設定 → 像素矩形 + 裁切。沒量測的 ROI 直接拋錯而不是
  給預設框硬跑。
- **`vision/tiles/segment.py`** —— 橘色斜面切牌。14/14 張、誤差 ±1px,
  並用斜面方向區分暗手牌與副露(對 GT 的副露數 9 與 13 驗證過)。
  這兩個模組都在功能 1 的路徑上,**繼續使用**。

## 五、被放棄的量測成果(保存備查)

以下座標都量測完成且目視驗證過,只是現在沒有消費者。
若日後要重啟牌河 CV,直接取用即可,不必重量。

**量測條件**:2560×1440 純畫布,座標相對 `table_rect` 正規化。
底圖是一局完整錄影(216 幀)加同一牌局四個視角的截圖疊出的極值圖
(東 4 局剩 14 張、牌河已疊到第三列、有四組副露)。

### 矩形 ROI `[x, y, w, h]`

```yaml
own:
  river: [0.3950, 0.5007, 0.2025, 0.2015]
  melds: [0.4108, 0.8711, 0.5392, 0.0948]
kamicha:            # 上家,螢幕左側(副露在下方,靠近自己這側)
  river: [0.2683, 0.2667, 0.1383, 0.2504]
  melds: [0.0325, 0.2681, 0.1492, 0.6281]
toimen:             # 對面,螢幕上方
  river: [0.4167, 0.1437, 0.1692, 0.1452]
  melds: [0.2058, 0.0311, 0.3550, 0.0563]
shimocha:           # 下家,螢幕右側(副露在上方)
  river: [0.5883, 0.2696, 0.1408, 0.2370]
  melds: [0.7825, 0.0370, 0.1175, 0.4785]
dora_indicators: [0.0133, 0.0385, 0.1475, 0.1319]
round_info:      [0.4142, 0.2948, 0.1750, 0.2000]
```

備註:

- `dora_indicators` 是**左上角那塊面板整塊**,不只寶牌指示器 —— 量測時刻意把
  下面那排「立直棒 ×N」「本場棒 ×N」的計數也框了進來。上半是 5 個寶牌槽
  (1 起始 + 最多 4 槓寶),下半約 1/3 高度是那兩個計數。
- `round_info` 是中央 HUD 整塊:局數、余牌數、四家點數、四角座位風標記
  (莊家紅底)。**本場與供託不在這裡**,在 `dora_indicators` 那塊面板。
- **牌河最多三列**(每列 6 張),不會有第四列 —— river 框剛好容納三列。
- `own_hand` 與 `own.melds` 的重疊不是錯誤:手牌靠左生長、副露靠右生長,
  副露越多手牌越短,兩者共用中間那段。

```yaml
  toimen:
    - [0.42150, 0.14285]
    - [0.57990, 0.14285]

  shimocha:

```

上家與下家的「一列 6 張」在畫面上是**垂直**方向(他們坐在左右兩側,牌河跟著
轉了 90 度),用這組座標時要記得把四個角轉到正確的軸。

### 網格四角為什麼只能手標

試過凸包多邊形逼近、四邊包絡線加穩健迴歸、最大連通元件過濾,四家都對不準。
**不是演算法的問題** —— 是參考畫面裡沒有任何一個牌河是滿的 18 格,右下角那格
從沒被填過,「右邊界的下段」與「下邊界的右段」兩條資料同時缺席,任何方法都
只是在對不存在的資料外推。人眼反而毫無困難,所以改用互動式拖四個角。

### 對手副露為什麼切不開

上家與下家的副露是**斜的**,而且他們的暗手牌是一整排實心橘色牌背 —— 與斜面
同色。試過把偵測方向改成左右向,四張參考圖全都只回傳 1 個合併的區塊。
把方向轉置解決不了問題,因為問題不在方向,在於「橘色」同時是斜面與牌背。
