# 即時模式操作手冊

`--live` 是實際使用的模式:一邊擷取畫面跑 CV(功能 1)、一邊抓封包餵引擎
(功能 2),兩條路的結果一起顯示在側邊視窗上。

錄製資料集的流程是另一件事,見 [recording.md](recording.md)。

---

## 一般情況

```bash
python tools/ui.py --live --mortal models/mortal_298k.pth
```

會發生的事,依序:

1. 側邊視窗開在螢幕右側(置頂)。**什麼都還沒開始** —— 瀏覽器沒開,兩個功能
   也都關著。
2. 按左下角的 **「開始遊戲」**。一個受控的 Chromium 開起來並載入網頁版雀魂,
   同時開始把封包錄到 `data/live/<時間戳>/ws.jsonl`。
3. 你在瀏覽器裡登入、開一場。
4. 撥開你要的開關(見下)。

**瀏覽器不會自己開,要按了才開。** 理由與兩個功能預設關閉相同:開一個瀏覽器
並開始往磁碟寫錄影檔該是明確的動作,不是打開視窗的副作用。

### 「開始遊戲」按鈕

| 按鈕的樣子 | 意思 |
|---|---|
| 綠色、可按 | 現在沒有遊戲在跑,按下去開一場 |
| 灰色「遊戲進行中」 | 瀏覽器開著。**要結束就關掉瀏覽器**,按鈕不做這件事 |
| 灰色「開始遊戲」 | 這個模式不由 MIA 開遊戲(重播 / 示範 / `--tail` / `--no-packets`) |

**關掉瀏覽器之後可以再按一次**,不必重開 MIA —— 這是它最主要的用途。

**每按一次就是新的一場,寫到新的錄影檔。** 不接在同一個檔案後面是必要的:
錄影檔是 append 模式寫的,而封包這條路是從**檔頭**讀的 —— 兩場疊在同一個
檔案裡的話,引擎會先把上一場整個重播一遍,然後拿著一個已經結束的牌局給建議,
**而且不會報錯**。

所以換場時,開著的「AI 建議」會自己重開一次去跟新的錄影檔(要再付一次載權重
的 0.5~0.6 秒)。第一場不會重開 —— 先打開 AI 建議再按開始遊戲也成立,那個
執行緒等的正是這一場要寫的檔案。

### 兩個開關

兩個功能**預設都不執行**,各自由所在頁面右上角的開關控制:

| 頁面 | 開關 | 打開之後 |
|---|---|---|
| AI 建議 | AI 建議 | 開一個 Mortal 子程序載權重(實測 **0.5~0.6 秒**),然後從錄影檔頭讀一遍把局面追上來 |
| 向聽分析 | 畫面辨識 | 開始持續擷取遊戲視窗、做牌桌校正、辨識手牌 |

預設關著不只是為了省資源:打開 AI 建議會開一個載著 130MB 權重的子程序、打開
畫面辨識會開始持續擷取螢幕。這兩件事都該是**明確的動作**,不是打開視窗的副作用。

**中途才打開也沒問題。** 錄影檔從一開始就在寫,而封包執行緒是從檔案開頭讀的
—— 座位、寶牌、誰立直了都補得回來,實測追完整場約 2 秒。

**擷取子程序不受開關影響**,一路開著。綁在開關上的話,關掉再打開會殺掉瀏覽器
—— 整場對局就沒了。

關掉開關會把那個功能在畫面上的產出一起清空。留著最後一手看起來像還在運作,
而那比空白糟得多 —— 使用者會照著一個已經不再更新的建議打牌。

`--no-vision` / `--no-packets` 與開關是兩件事:那兩個旗標讓對應的功能**整個
不存在**,所以它的開關會畫成停用(而不是可按但撥不動)。

### 畫布尺寸(向聽分析頁,**建議一開始就選**)

向聽分析頁的設定列上有一個「畫布」選單:自動偵測 / 1280×720 / 1600×900 /
1920×1080 / 2560×1440。

選了之後,下一次按「開始遊戲」會把瀏覽器視窗調到讓**頁面畫布剛好等於**那個
尺寸,畫面辨識就不必再猜牌桌邊界在哪 —— 矩形是算出來的,一幀就鎖定。

**這件事很值得做。** 自動偵測是啟發式,實測在某些視窗尺寸下(例如 900×593)
會安靜地鎖進一個偏掉約 0.7 張牌寬的矩形,手牌辨識的每張牌正確率從 96% 掉到
29%,而過程中沒有任何錯誤訊息。詳見 `docs/decisions.md` 第十六節。

挑哪一個:選**螢幕放得下的最大值**。放不下的話瀏覽器不會照做,狀態列會說
「畫布尺寸對不上目前的視窗」,換小一個就好。Retina 螢幕記得畫布 1280×720
擷取到的是 2560×1440,牌面像素其實是那個的一半 —— 1280×720 已經夠用。

兩個限制:

* **對局中途改不會讓瀏覽器變大小。** 尺寸是開視窗時下的命令,要下一次
  「開始遊戲」才生效。中途改的話畫面辨識會先說「畫布對不上」,那是實話。
* **`--connect`(連到你自己開的瀏覽器)時選單無效。** 那個視窗不是 MIA 開的,
  不該去動它。那種情況請自己把視窗調成 16:9 畫布,或用 `manual_table_rect`。

### Overlay(疊在遊戲上的 HUD)

側邊視窗要看得清楚就得夠大,而眼睛得在牌桌與它之間來回跳。Overlay 把最重要
的那一行直接疊在遊戲畫面上。

開關在**設定頁**,三個勾選:

| 勾選 | 作用 |
|---|---|
| 在遊戲上顯示 Overlay | 顯示 / 收起來。預設收著 |
| Overlay 顯示候選 Q 值 | 精簡(一行)↔ 展開(多前 5 個候選與長條) |
| 鎖定位置(滑鼠可穿透) | 見下 |

精簡的樣子:

```
┌────────────────────────────┐
│  切 [3s]    │  一向聽 進張 12 │
└────────────────────────────┘
```

左半是 AI 建議(吃會畫出「用哪兩張」、立直會畫出「之後切哪張」,與側邊視窗
同一份邏輯),右半是向聽與進張。哪一邊的功能關著,那一邊就整段收起來。

**擺位置:沒鎖定時直接用滑鼠拖。** 拖好之後到設定頁勾「鎖定位置」——
鎖定之後點擊會直接穿到底下的遊戲,不會被 Overlay 擋住。反過來說,**鎖定
狀態下拖不動**,要移動就先解鎖。沒鎖定時 Overlay 會畫一圈綠色虛線,那就是
「現在拖得動」的意思。

位置與三個勾選都記在 `data/ui_state.json`,下次啟動回到同一個地方。那個檔案
壞掉或刪掉都不影響程式,只是回到預設位置(螢幕上緣置中)。

**四種模式都有 Overlay** —— `--demo` 與 `--replay` 也看得到,截圖不必開遊戲。

> ⚠ **用 mss fallback 時要讓 Overlay 避開手牌。** 主路徑是單視窗擷取,抓的是
> 視窗自身的緩衝區,疊在上面的東西不會進到辨識輸入;但 mss 抓的是螢幕,會把
> Overlay 一起拍進去。退回 mss 時終端機會警告。

封包錄影會寫到 `data/live/<時間戳>/ws.jsonl`,路徑在啟動時印在終端機上。
**那份檔案就是 GT 素材** —— 打完可以直接拿去跑
`tools/evaluate.py` 與 `tools/advise.py`,不必為了產生資料集再打一場。

結束:關掉側邊視窗,或在終端機按 Ctrl-C。兩者都會走正常的關閉流程
(引擎子程序、Chromium 一起收掉)。

### 保留登入狀態

**預設就會留著**,在 `data/live/chrome-profile`。第一次登入之後就不必再登。

這個旗標本來沒有預設值,要自己在命令列補上 —— 結果是「忘了加就每次都要重新
登入」,而那個退化沒有任何症狀可循:程式一切正常,只是雀魂不認得你。

要換一個位置,或是真的想要一個乾淨的設定檔(測第一次登入流程):

```bash
python tools/ui.py --live --user-data-dir /somewhere/else
python tools/ui.py --live --fresh-profile     # 用完就丟,不留登入
```

### 只跑其中一條路

三個功能刻意解耦,一邊壞掉另一邊照樣有用:

```bash
python tools/ui.py --live --no-vision --mortal models/...   # 只要 AI 建議
python tools/ui.py --live --no-packets                      # 只要向聽分析
```

`--no-vision` 的額外好處:不需要 macOS 的螢幕錄製授權。

### 用自己平常的瀏覽器 / Steam 桌面版

```bash
# 連到已開的 Chrome(需以 --remote-debugging-port=9222 啟動)
python tools/ui.py --live --connect http://localhost:9222 --mortal models/...

# Steam 桌面版:另一個終端機用 MITM 錄,這邊只跟著檔案走
python tools/gt.py local --spec Jantama_MahjongSoul --out data/live/now/ws.jsonl
python tools/ui.py --live --tail data/live/now/ws.jsonl --mortal models/...
```

`--tail` 不會自己開擷取子程序,所以不會跟另一個錄製程序搶同一個瀏覽器。

> MITM 兩種模式的 CA 憑證**尚未實測**。雀魂桌面版是 Unity 客戶端,
> 它的網路堆疊會不會查詢系統憑證信任清單目前還不知道。

## 狀態列在說什麼

狀態列是唯一的診斷介面 —— 工作執行緒不會拋例外中斷,任何一步不成立就在這裡
說一句話然後繼續轉。訊息前綴是哪一條路出的問題。

| 訊息 | 意思 | 怎麼處理 |
|---|---|---|
| `還沒開始 —— 按左下角的「開始遊戲」開啟遊戲` | 正常,剛開起來 | 按那顆按鈕 |
| `兩個功能都關著` | 正常,遊戲開了但兩條路都沒跑 | 撥開你要的那個開關 |
| `封包擷取:擷取子程序啟動中` | 正常,瀏覽器還在開 | 等它,然後登入 |
| `封包擷取:擷取子程序啟動 N 秒就結束了` | 通常是 Playwright 沒裝或瀏覽器沒下載 | 看終端機的訊息;`playwright install chromium` |
| `封包擷取:封包擷取已結束` | 你關掉瀏覽器了 | 正常。要再打一場就再按一次「開始遊戲」 |
| `封包:啟動引擎…` | Mortal 在載權重 | 實測 0.5~0.6 秒,一閃而過 |
| `封包:引擎啟動失敗` | 權重路徑錯、`engines/mortal/.venv` 沒建、上游沒 clone | 訊息裡會指名少了哪一個 |
| `封包:等待對局開始` | 一切正常,還沒進對局 | 去登入、開一場 |
| `封包:在對局中途接上` | 事件流裡還沒出現 `start_game` | 這一場沒辦法了,下一場會有。原因見下 |
| `封包:<引擎名> 掉隊` | 那個引擎崩了或逾時 | 其他引擎照常;要救得重開 |
| `畫面:找不到遊戲視窗 —— 雀魂開著嗎?` | 視窗比對沒命中 | 遊戲真的開了嗎?視窗太小也會被排除 |
| `畫面:擷取後端無法使用` | macOS 沒給螢幕錄製權限 | 系統設定 → 隱私權與安全性 → 螢幕錄製 |
| `畫面:牌桌校正中 N/M` | 正常,在蒐集多幀取中位數 | 等幾秒。停在這裡不動見下 |
| `畫面:牌桌校正失敗:最近 N 幀有 M 幀認不出牌桌邊界` | 自動偵測在這個視窗尺寸下不管用 | **在向聽分析頁選一個畫布尺寸**,再按一次「開始遊戲」 |
| `畫面:牌桌校正失敗:畫布尺寸 X 對不上目前的視窗` | 選的尺寸與實際視窗不符 | 螢幕放不下就換小一個;或是對局中途才改的,按「開始遊戲」重開一場 |
| `畫面:擷取失敗 N 次` | 視窗被最小化或剛關掉 | 連續 15 次會自動重找視窗 |
| `畫面:讀到 N 張,不是合法手牌` | 抓在理牌或摸打的動畫中間 | 正常會自己過去。**一直卡著**代表 ROI 對不上 |
| `畫面:CV 對部分牌沒有把握` | 模板比對分數偏低 | 皮膚換過?`tools/fetch_tiles.py` 抓對應皮膚 |
| `畫面:設定裡沒有 own_hand ROI` | 設定檔那一項是 null | 跑 `tools/roi_annotate.py` 量測 |

### 幾個「看起來卡住」的情況

**校正一直停在 `N/M`** —— 校正靠剝除四周純色邊框,而載入畫面與選單正是最容易
失敗的時候。進到牌桌畫面就會鎖定。真的鎖不住的話會自己變成「校正失敗」,
那時候去選一個畫布尺寸(上面那一節);還是不行就用 `config/default.local.yaml`
手動指定 `manual_table_rect`。

**手牌一直「不是合法手牌」** —— 校正鎖到了錯的矩形,ROI 整體位移。先選一個
固定畫布尺寸再試一次 —— 那會把矩形從猜的換成算的。還是不對才需要用
`tools/roi_annotate.py` 對著當下的畫面重量一次。

**畫面上寫「未開啟」** —— 那一頁的功能還沒打開。撥右上角的開關。刻意不沿用
「等待引擎…」那句話:功能關著的時候那會讓人以為它正在載入,於是一直等下去。

**遊戲跳出「碰 / 槓 / 跳過」時,大字會是「跳過」** —— 那不是「沒有建議」,
那就是建議。底下的候選清單會把三個選項的 Q 值並排,所以看得出差多少:

```
跳過   -0.15  ████████████████
碰     -6.30  █
槓     -6.55
```

差 6 分是「明顯不該鳴」;若是 `碰 -0.11` 對 `跳過 +0.10`(實測真的有),
那就是一個近乎五五波的判斷,值得自己再想一下。

**建議顯示「切 3s」但手上沒有 3s,而且字是灰的、後面有「·已打出」** ——
這是正常的。手牌與建議是兩個獨立的更新槽,打牌的事件到了、手牌變成 13 張,
但建議還是上一巡算出來的。灰字就是在說「那一手已經打完了」。

**中途接上為什麼救不回來** —— MJAI 引擎的座位、寶牌、誰立直了全都來自
`start_game` 與之後的事件。雀魂只在 `authGame` 時送 `start_game`,也就是進場的
那一刻。所以從對局中途開始錄,這一場就沒有完整的局面可以重建 —— 硬餵下去
引擎會給出看起來正常但其實錯的建議,那比沒有建議糟。

正常流程不會遇到:擷取子程序是 MIA 自己開的,瀏覽器從登入開始跑。
用 `--tail` 接一份已經在錄的檔案時才可能撞到。

## 效能

| 項目 | 實測 |
|---|---|
| 擷取 | 15 fps(可調 `capture.target_fps`) |
| 畫面沒變的幀 | 整幀跳過,不做模板比對 —— 一巡之內大部分時間都是這種 |
| Mortal 推論 | 10~23 ms/決策 |
| UI 套用間隔 | 100 ms |

100 ms 的 pump 間隔不會漏資訊:郵箱會把這段時間內的更新合併掉,只是畫面晚
0.1 秒 —— 遠小於遊戲自己的動畫時間。

如果覺得手牌顯示落後於實際,那不是 pump 間隔的問題,而是某一條路卡住了 ——
看狀態列。

## 還沒驗過的

* **畫面與封包同時在真實對局上跑。** 兩條路各自都在真實素材上驗過了,
  但沒有一起跑過一場。
* **`own_hand` ROI 在即時擷取下的位置。** 測試是把手牌截圖貼進合成畫面,
  位置是自己安排的。
* **Overlay 疊在真的遊戲視窗上。** 版面與開關都驗過了(單元測試 + `--demo`
  截圖),但沒有實機疊在對局上看過 —— 尤其是「鎖定之後點擊真的穿到遊戲」與
  「焦點在瀏覽器時 Overlay 不會被 macOS 藏起來」這兩件事,只有實機能驗。
* **Windows。** 擷取層寫好了,沒有機器測過。
