# 用畫面產出 MJAI 事件流:還缺什麼

**寫給誰:** 做 Steam 版圖像辨識的組員,以及之後要接線的人。

Steam 版的雀魂是 Unity 客戶端,**沒有封包可攔**。所以 AI 建議與放銃分析在那一版
上唯一的資料來源是畫面。接點在 `decisions.md` 第二十一節已經定好:

```
圖像辨識  →  MjaiEvent 串流  →  PacketWorker / DangerWorker
```

**放銃分析本身一行都不用改。** 它吃的是 `MjaiEvent`,不在乎那些事件是封包解出來
的還是畫面認出來的。接上之後改的是 `mia/platforms.py` 的 `SUPPORTED` 那一行。

所以問題不是「放銃分析能不能用 CV 做」,而是「CV 能不能產出它要的那些事件」。

---

## 放銃分析要的比 Mortal 少得多

這件事決定了優先順序,值得先講。`TableTracker.handle()` 只對這些型別有反應,
其他一律忽略:

| 事件 | 要的欄位 | 拿來做什麼 |
|---|---|---|
| `StartGame` | `id` | 知道自己坐哪 |
| `StartKyoku` | `bakaze`、`oya`、`dora_marker` | 清空上一局 + 算每家的役牌 |
| `Dahai` | `actor`、`pai` | **振聽與筋的全部依據** |
| `Reach` | `actor` | 指名威脅 |
| `Chi`/`Pon`/`Daiminkan` | `actor`、`target`、`pai`、`consumed` | 壁的張數 + 副露組數 |
| `Ankan`/`Kakan` | 同上 | 同上 |
| `Dora` | `dora_marker` | 役牌與壁 |

**不需要**的:別家的 `Tsumo`(`pai` 填 `?` 就夠)、`Hora`、`Ryukyoku`、點數、
本場、供托。Mortal 要這些,放銃分析不要。

所以可以先做出一條**只餵放銃分析**的事件流,不必等整條串流完整。

## 缺口,由難到易

### 1. `Dahai` —— 把「牌河的狀態」變成「捨牌的事件」(中)

牌河辨識回的是**一條河現在有哪些牌**,而 MJAI 要的是**誰剛打了什麼**。
中間差一個變化偵測。

看起來只要 diff 就好,但有三個坑:

* **鳴牌會讓河縮短並往前遞補。** 雀魂不留空位 —— 被鳴走那一格會空出來,
  後面的牌整排往前移(見 `mia/mjai/table.py` 的 `Player.visible_river`)。
  所以「這一幀比上一幀少一張」不是錯誤,是鳴牌。天真的 diff 會把整排錯位
  當成一連串捨牌。
* **一幀之間可能發生不只一件事。** 錄影是取樣的,兩張捨牌之間若掉幀,
  就得補出順序。
* **立直橫放的那張牌會撐開格線。** 見下一條。

### 2. `Reach` —— 而且它同時是 1. 的前提(中,且現在是個靜默的洞)

立直宣言牌是**橫放**的,佔的寬度和直放不一樣。而牌河辨識用的是固定 6x3
等寬格線,**完全沒有處理這件事**(`river.py` 裡沒有任何一處提到立直)。

實測在 `20260801-110639` 的一幀上肉眼確認:上家第二排那張橫放的牌跨過格線,
那一格被判成空的。

兩件事要一起看:

* 對 `Reach` 事件而言,橫放那張牌**就是**訊號 —— 偵測到它就知道誰立直、
  第幾張捨牌是宣言牌(`reach_turn` 要的正是這個)。
* 對牌河辨識而言,它現在是**錯誤來源**,而且錯在立直之後的每一張牌上。

所以這一條做對了是一石二鳥,不做則是一個會一直累積的偏差。
**這是我認為該第一個做的。**

> ⚠ 未量化:94.6% 那個數字是在有四次立直的錄影上量到的,所以影響顯然沒有
> 「整條河全毀」那麼嚴重。但沒有人分開量過「立直前 vs 立直後」的正確率。
> 動手之前先補這個量測。

### 3. 副露事件(難,但也許不是當初那個難法)

`decisions.md` 第五節記著一次失敗:上家與下家的副露是**斜的**,而他們的暗手牌
是一整排橘色牌背 —— **與斜面同色**。四張參考圖全部只回傳一個合併的區塊。
結論是「切不開」,整層拿掉。

那個結論對**當時的問法**成立:從一張靜態圖裡把副露區切成一組一組。

但 MJAI 要的不是那個。它要的是一個事件:「上家在第幾巡碰了什麼」。那是
**變化偵測** —— 某一家的副露區從空的變成多了三張**正面朝上**的牌,而且時機
是緊接在某人打出某張牌之後。已知的約束很強:

* 被鳴的那張牌 (`pai`) 就是上一個 `Dahai` 的牌 —— 不必從畫面認。
* `target` 就是上一個打牌的人。
* 只剩 `consumed`(他自己拿出來的那兩三張)要從畫面認,而那幾張是正面朝上的。
* 吃/碰/槓由張數與來源方向區分。

**這不等於它會成功**,只是說當初那個「切不開」的證據不直接適用。
要先做一次可行性實驗,不要直接當成已解決。

### 4. `Dora` 與局的邊界(易)

寶牌指示牌在畫面上固定位置,座標量過(`decisions.md` 第四節,ROI 後來刪了)。
槓之後會多翻一張,所以是「現在有幾張」而不是「一張」。

`StartKyoku` 要的 `bakaze` / `oya` 在 HUD 上。局的邊界也可以用「四家牌河同時
清空」來偵測 —— 那個訊號很強。

### 5. 動畫遮擋(已知,已經有防線)

立直/和了的立繪會整個蓋住牌河。角色的皮膚色是「亮、不飽和」,與牌面的判斷
條件一模一樣,所以動畫會被讀成一排牌。

實測 1012 條牌河裡 160 條(15.8%)受影響,而**連續性檢查正確擋下了它們** ——
那道閘在做對的事。對事件流而言這代表:那些幀直接跳過即可,不要試圖從中讀出
捨牌。影響的是延遲(等動畫播完),不是正確性。

## 建議的順序

1. **先量**:立直前 vs 立直後的牌河正確率。那決定第 2 條的規模。
2. **做 `Reach` + 橫放牌的格線**。一石二鳥,而且它是 `Dahai` 的前提。
3. **做 `Dahai`**(含鳴牌造成的遞補)。做到這裡,振聽與筋就有了 ——
   那是放銃分析四條排除法裡的兩條,而且是最常觸發的兩條。
4. **做 `Dora` 與局邊界**。壁與役牌有了。
5. **最後才碰副露**,而且先做可行性實驗。沒有它的時候,放銃分析會少算
   「壁」的張數與「3副露」這個威脅標籤 —— 兩者都是**低估威脅**的方向,
   也就是會把危險牌說成比較安全。這件事必須在 UI 上講明白,不能默默少算。

最後那一句是這個專案一貫的原則:少算要讓人知道,因為它錯的方向是危險的那邊。
