# 目標:用畫面產出完整的 MJAI 事件流

**定於 2026-10-24。** 這是一個**方向**,不是一個已完成的設計。

**寫給誰:** 做 Steam 版圖像辨識的組員,以及之後要接線的人。

---

## 一、目標與它的範圍

```
畫面  →  MjaiEvent 串流  →  PacketWorker / DangerWorker / Mortal
```

接點在 `decisions.md` 第二十一節就定好了,而且**下游一行都不用改** ——
它們吃的是 `MjaiEvent`,不在乎那些事件是封包解出來的還是畫面認出來的。
接上之後改的是 `mia/platforms.py` 的 `SUPPORTED` 那一行。

這件事的意義不只是「多支援一個平台」。網頁版有封包,CV 做的是重複的工;
Steam 版**沒有封包**,CV 是唯一來源。所以這條路通了,整個專案才不再被
「必須攔得到封包」綁住。

### 兩個消費端的要求差很多

這決定了做事的順序,值得第一個講。

| | 放銃分析 | Mortal |
|---|---|---|
| 要哪些事件 | 8 種 | 全部 17 種 |
| 別家的 `Tsumo` | 不要 | 要(`pai` 可填 `?`) |
| 點數 / 本場 / 供托 | 不要 | 要 |
| `Hora` / `Ryukyoku` | 不要 | 要 |
| **對錯誤的容忍** | **高** | **低** |

最後一列是關鍵。放銃分析少讀一張捨牌,只是少一張現物,狀態不會垮;
Mortal 吃的是**有狀態**的串流,一個錯的 `Dahai` 送進去,之後整局永久偏掉 ——
而且它不會報錯,只會對著一手你沒有的牌給建議。

**所以先做一條只餵放銃分析的串流,再往 Mortal 擴。** 不是因為 Mortal 比較難
認,是因為它比較不能錯。

## 二、為什麼這次和 2026-07-29 不同

那天的 commit(`817a11c`)把整條牌河 CV 砍掉,理由寫得很明白:

> 放棄牌河 CV 的直接原因是**立直橫放牌破壞了 6x3 均勻網格的假設**,
> 而牌河換來的完整對局狀態封包路徑已經 100% 拿得到。

兩個理由,現在的狀況都變了:

* **「封包已經拿得到」** —— 對網頁版成立,對 Steam 版不成立。而 Steam 版
  是專題的終點(`decisions.md` 第二十一節)。
* **「辨識還不夠好」** —— 當時沒有的東西現在有了:

  | | 2026-07-29 | 現在 |
  |---|---|---|
  | 每張牌正確率 | 未量 | 94.6% |
  | 靜默錯誤 | 未量 | 0.24% |
  | 棄權機制 | 無 | 兩個尺度不一致就不表態 |
  | 牌桌矩形 | 自動校正會跳(216 幀 21 種) | 手動框 + 自動微調,實測 88% |

**但第一個理由裡的那件事還在。** 立直橫放牌到今天仍然沒有被處理 ——
`river.py` 裡沒有任何一處提到立直,用的是固定 6x3 等寬格線。
2026-10-24 在 `20260801-110639` 的一幀上肉眼確認:上家那張橫放的牌跨過格線,
那一格被判成空的。

**它七月擋住了整條路,今天還在那裡。** 這就是第一順位。

### 已經重生的東西,與從來不存在的東西

同一個 commit 刪掉的 `vision/grid.py`(154 行,四角 + 單應變換把每一格反扭回
正矩形)**已經重生** —— 現在的 `RiverView.rectify` 與 `DEFAULT_CORNERS` 就是
它的後繼,而且調得更好。

但同時刪掉的 `tracker/` 層是個 **0 bytes 的空套件** —— 那層**從來沒有寫過**,
只被規劃過。它要做的事(把逐幀觀察拼成事件流、做規則校驗)是這條路上最大的
一塊新工程,而且沒有舊程式可以撿。

## 三、錯誤率:算清楚它會長成什麼樣

每張牌靜默錯誤 0.24%(實測,已經是兩個尺度一致才採信的版本)。推到實戰尺度:

| | 至少一個靜默錯誤 |
|---|---|
| 自己一手 14 張 | 3.3% |
| 一局四家約 70 張捨牌 | **15.5%** |
| 一場八局 | **74.0%** |

對 Mortal 而言 74% 是不能用的。

### 結構上的優勢:牌河是永久的

手牌每秒都在變,但一張**打出去的牌會留在桌上到這一局結束** —— 同一張牌有
幾百幀可以重讀。假設錯誤獨立,多數決的效果是:

| | 每張牌 | 一局 70 張 |
|---|---|---|
| 單幀 | 2.4e-03 | 15.5% |
| 3 幀多數決 | 1.7e-05 | 1.2e-03 |
| 5 幀多數決 | 1.4e-07 | 9.6e-06 |

### 但那個假設被自己的資料打臉

實測 273 個靜默錯誤裡 **272 個是同一種**:`2m → 1m`,而且錯的那個分數還比較高。

那是**系統性混淆,不是雜訊**。投票一千幀會得到一千次同樣的錯答案。

所以上面那張表是**樂觀上界**,不是預期值。對付系統性錯誤的工具是**棄權**
(已經做好:兩個尺度不一致就不表態,靜默錯誤 0.65% → 0.18%),而棄權把問題
換成另一個:

> MJAI 不能說「他打了一張我不知道是什麼的牌」。`Dahai` 必須指名一張牌。

好消息是**延遲預算很寬**:狀態只要在自己下一次該動作之前補齊就好,那是好幾秒、
上百幀。而且動畫會播完、牌還在那裡。**棄權不等於放棄,等於延後。**
那正是 `tracker` 層要處理的事。

### 缺的,由難到易

#### 1. `Reach` 與立直橫放牌(中,且現在是個靜默的洞)

見第二節。一石二鳥:橫放牌**就是** `Reach` 的訊號,而 `reach_turn` 要的正是
「第幾張捨牌是宣言牌」;同時它是牌河格線目前的誤差來源。

#### 1.1 量測結果(2026-10-24)

在 `20260801-110639` 上量,每 3 幀取一,共 641 幀。把每一張牌依它在那一家
牌河裡的位置分成四類:

| 類別 | 張數 | 正確率 | 有信心 | 靜默錯誤 |
|---|---|---|---|---|
| 沒立直(全體) | 13714 | 95.8% | 11893 | 0.91% |
| 　對家(本次唯一的立直家) | 2708 | **91.9%** | 2199 | 0.00% |
| 宣言牌之前 | 444 | 86.7% | 362 | 1.38% |
| **宣言牌本身** | 59 | **0.0%** | **0** | 0.00% |
| **宣言牌之後** | 229 | **61.6%** | 100 | **0.00%** |

**三個結論:**

1. **橫放的宣言牌從來沒認對過。** 59 張,0 次。模板比對看到的是一個轉了
   90 度的東西,那對 `TM_CCOEFF_NORMED` 來說就是另一張牌。
2. **它後面的牌掉 30 個百分點**(對家自己的基準 91.9% → 61.6%)。
   格線確實被推掉了。
3. **但全部表現為棄權,不是錯誤。** 宣言牌本身「有信心」0 次,宣言牌之後的
   靜默錯誤 0.00%。**而且採用率完全沒受影響** —— 橫放牌仍然被判定為
   「這一格有牌」,所以不會破洞;126 條被連續性擋下來的牌河**全部**來自
   沒立直的家(那些是立繪動畫,見第 6 條)。

第 3 點是這一步最重要的發現,它改變了這塊擋路石的形狀:

> 2026-07-29 放棄時,它是「格線假設被破壞」—— 聽起來像地基塌了。
> 今天它是「有一格會說我不知道,而它後面幾張的把握度下降」。
> 棄權在事件流裡是可以處理的(牌還在桌上,下一幀再讀);
> 「有信心卻是錯的」才不行,而那一欄是 0。
>
> 中間的差別是**兩個尺度一致才表態**那道機制 —— 七月沒有它。

#### 1.1b 修它的第一次嘗試:失敗,已回退(2026-10-24)

**結論:用「寬度」去偵測橫放牌行不通。三次都是淨負的,已經整組退掉。**

想法是對的,而且量到的幾何是可信的:

* 橫放牌在攤平圖上寬 110~115 px,正常牌 85~88,一格 90 —— 寬約 1.3 倍。
* 它後面的牌往右推約 27 px(0.3 格)。
* **位移只影響同一列。** 實測下一列的牌面區段與格線完全對齊,
  因為每一列都從左邊重新開始。

套上去之後「宣言牌之後」從 61.6% 跳到 **91.3%** —— 修法本身是有效的。

**壞在偵測,不在修正。** 三次都敗在同一件事:

| 門檻 | 沒立直的上家 | 誤報率 |
|---|---|---|
| 寬 > 1.12 格 | 99.1% → **74.4%**,靜默錯誤 0.00% → 2.50% | — |
| 1.12 ~ 1.50 格 | 99.1% → 86.4% | 18.7% |
| 自己中位數的 1.18~1.55 倍 | — | **22.9%** |

去看誤報的圖才懂:**每一家的「正常牌寬」本來就不一樣**。上家與下家的
視角壓得扁,牌與牌之間的桌布縫隙幾乎消失,而且還看得到側面那條橘邊。
牌會不固定地黏成一段 —— 而那也毀了中位數這個基準:它不再是「正常牌寬」,
而是「幾張黏在一起的平均」。

算總帳:救回 229 x 30% ≈ 69 張,賠掉 13692 x 4.1% ≈ 561 張。**淨負。**

##### 下次該試什麼(而不是再調一次門檻)

問題出在**切割**:把一條河切成「幾段牌面」這件事本身在上家/下家不可靠。
所以不要再從切割下手。

**我們已經知道牌應該在哪。** 與其切割,不如逐格問一個分類問題:
「第 k 格裡的東西,比較像直放的牌,還是像轉了 90 度的牌?」那可以用
現成的 :func:`~mia.vision.tiles.classify.classify` 回答 —— 把模板轉 90 度
再比一次,哪一邊分數高就是哪一邊。

好處是它完全不需要切割,而且**用的是已經驗證過的機制**(模板比對),
不是又一個新的啟發式門檻。

另外:一列裡有橫放牌時,那一列**真的比 6 格寬**,第 6 張牌有一部分落在
`DEFAULT_CORNERS` 的四邊形之外 —— 根本沒被 rectify 進來。那不是對齊問題
是資料不存在,要修得把四邊形放寬,而那會動到所有既有的量測基準。

#### 1.2 這個量測的限制(重要)

**全部的立直樣本都來自對家一個人。** 不是取樣邏輯的問題,是素材:

```
畫面錄了  848 秒
封包錄了 1433 秒     ← 錄影比封包早結束將近 11 分鐘
```

這份錄影一共 12 局、7 次立直(自己 2、下家 2、對家 2、上家 1),
但落在畫面區間內的立直狀態:

| | 時間軸上 | 畫面涵蓋到 |
|---|---|---|
| own | 8 | 2 |
| shimocha | 42 | 1 |
| toimen | 55 | **54** |
| kamicha | 8 | **0** |

而四家的難度本來就差很多(同一份錄影:上家 99.1%、對家 91.9%,差 7 個百分點),
所以 **61.6% 這個數字確立的是方向,不是幅度。**

「宣言牌之前」比對家自己的基準低 5 個百分點(91.9% → 86.7%,444 張)——
**沒有解釋**。位置沒動的牌不該變差。樣本不大,也可能是立直後那一家的畫面
狀況整體不同。先記著,不要編理由。

**要補的素材:** 一次畫面與封包**涵蓋同一段時間**的錄製,而且要有不只一家
立直。`decisions.md` 第八節的「待補的一次錄製」就是在講這件事。

#### 1.3 補錄之後(`20261024-123746`,2026-10-24)

用 `tools/capture.py --autoplay mortal` 錄的:4 局、447 秒、4533 幀
(1642 個可評分),立直來自**下家 2 次、自己 2 次** —— 兩個舊素材量不到的座位。

| 類別 | 張數 | 正確率 | 靜默錯誤 |
|---|---|---|---|
| 沒立直 | 3929 | **95.0%** | 0.72% |
| 　自己 | 743 | 97.6% | 0.00% |
| 　下家 | 900 | 96.3% | 0.00% |
| 　對家 | 1058 | 95.4% | 0.77% |
| 　上家 | 1228 | 92.1% | 1.55% |
| 宣言牌之前 | 58 | 96.6% | 0.00% |
| **宣言牌本身** | 16 | **0.0%** | 0.00% |
| **宣言牌之後**(下家) | 42 | **33.3%** | 0.00% |

**三件事:**

1. **辨識器本身是穩的。** 95.0% 對上舊素材的 95.8% —— 換了一份完全不同的
   錄影、不同的座位分布、而且這份是機器人打的,數字仍然站得住。
2. **橫放牌 0% 是普遍的。** 自己與下家兩個新座位,16 張全部認不出來、
   全部沒把握。不是對家特有的現象。
3. **「之後」的損害比第一次量到的大得多。** 對家 91.9% → 61.6%(掉 30),
   **下家 96.3% → 33.3%(掉 63)**。1.1 節那句「61.6% 確立的是方向不是
   幅度」的但書是對的,但幅度比預期更糟。

順帶解掉一個懸案:1.1 節記著「宣言牌之前比基準低 5 個百分點,沒有解釋」。
新素材是 96.6%,**比基準還高**。所以那 5 個百分點是樣本雜訊,不是真實效應
—— 位置沒動的牌確實不受影響,當時不編理由是對的。

#### 1.4 修好了:旋轉模板 + 「挪了有沒有變好」(2026-10-24)

**結論:宣言牌之後的牌從 62.8% / 37.5% 變成 100% / 100%,而沒立直的那幾家
一位小數都沒動。假陽 0/92。**

程式碼:`mia/vision/tiles/river.py` 的 `find_sideways()`、`classify_sideways()`、
`read_river(sideways=...)`、`River.clipped`,以及
`classify.py` 的 `TemplateSet.rotated()`。

##### 為什麼要三道關卡

1.1b 說的方向是對的(逐格問「像直放還是像轉過的」),但**單獨用完全不夠**。
量出來的分佈中心分得很開 —— 正常牌中位 −0.32、宣言牌 +0.06~+0.12 —— 可是
尾巴重疊,而且重疊的方向最糟:**有正常牌比每一張真宣言牌都更像橫放**
(正常牌最大 +0.270,正例最高只有 +0.122)。逐格設門檻一定夾不住。

所以加關卡,而每一關都是因為前一關被量到不夠才加的:

| 候選規則 | 召回 | 假陽 |
|---|---|---|
| 旋轉分數差 ≥ 0 | 100% | 16% |
| ＋直放認不出來 | 100% | 6% |
| ＋挪了之後認得出來的牌變多 | **94.6%** | **0%** |

第二關是免費的:宣言牌 **221/221 格**都過不了 `CONFIDENT` —— 它真的沒有
直放,直放模板本來就認不出它;而正常格子有六成多是認得出來的。

第三關才是拍板的那一關。前兩關剩下的 92 個假陽裡 **51 個是九筒** ——
九筒是 3x3 的圓點,**轉九十度跟原來幾乎一樣**,所以「像不像轉過的」這個
問題對它原則上無解,再調門檻也不會改善;另外 33 個的答案是 `None`,
那些格子根本沒有牌(動畫殘影)。那就別再問那個問題,直接問我們真正在意的事:

> 假設這格橫放、把同一列後面的格子往右挪 27 px,**認得出來的牌有變多嗎**。

真的橫放牌後面本來全偏著,挪完會對回來;九筒誤判後面本來是對的,挪完會壞掉。
實測 56 個可驗的假陽:33 個沒變、23 個變差、**0 個變好**。

附帶一個很乾淨的性質:宣言牌是當列最後一張時沒有東西可以驗,於是不判定 ——
**而那時候它也還沒害到任何人**(它只錯自己那一張,後面還沒有牌)。
偵測器只需要在有影響的時候正確,而剛好就在那時候驗得出來。

##### 1.1b 預告的那個坑真的掉進去了

1.1b 最後一段寫著「一列裡有橫放牌時那一列真的比 6 格寬,第 6 張有一部分
落在四邊形之外」。第一版把那一格判成**沒牌**,於是牌河破洞、連續性檢查把
**整家這一幀**丟掉 —— 舊素材 10 次、新素材 5 次,全在立直之後。那等於用
「扔掉整家」去換「宣言牌之後的正確率變好看」,而被扔掉的其他五張本來讀得到。

改成 `River.clipped`:有無仍然用**沒挪的位置**判(張數與連續性才對得上),
但那一格標成「知道有牌、讀不到」,上層棄權。把四邊形放寬才是根治,
而那會動到所有既有的量測基準 —— 那是另一件事,不在這一步。

##### 旋轉模板的尺寸:又一個「以為是交換」的假設

第一版把旋轉模板的尺寸寫成直放牌面的**寬高交換**(0.70 x 0.72)。掃出來的
最佳值是 **1.22 x 0.49** —— 寬得多、矮得多,長寬比 2.49 而交換只會給 1.29。
躺下來之後透視壓縮的軸也跟著換了,不是單純的轉置。

分數因此從 0.53 升到 0.65~0.81。掃描(兩份錄影、4 張宣言牌,各取三幀):

| 牌 | 最佳尺寸 | 分數 |
|---|---|---|
| 自己 5m | 114x55 | 0.807 |
| 下家 5p | 110x59 | 0.733 |
| 對家 5m | 106x59 | 0.794 |
| 對家 2m | 102x59 | 0.731(認錯) |

**最佳值跟著座位走** —— 離鏡頭越近越大。取中間值 110x59
(`SIDEWAYS_FACE`),四家都堪用。只有 4 張牌,分家調就是對單一樣本過擬合。

##### 宣言牌的身分:**刻意**不給信心

尺寸修好之後出現一個退步,而且正好在最該守的那一欄:

| | 正確率 | 有信心 | 靜默錯誤 |
|---|---|---|---|
| 交換尺寸(0.53) | 0.0% | 0 | 0.00% |
| 量出來的尺寸 | 54.5% | **10** | **100.00%** |

分數過了 0.60、差距也過了 0.10,於是它開始**有信心地把 2m 說成 1m**。
正確率上升,但換來有信心的錯誤 —— 在放銃分析裡這個交換是賠的。

所以 `classify_sideways()` 把次高分設成與最高分相同,**差距歸零、永遠過不了
任何門檻**,標籤與分數仍然留著給診斷看。寫法沿用 `classify_river_tile`
兩個尺度不一致時的做法。

理由不是「分數不夠」而是**證據不夠**:直放那條路的門檻掃過 1921 幀,
橫放這條路總共只有 4 張不同的宣言牌,其中一張在任何尺寸下都認錯。
要放寬這一條,先拿出更多宣言牌的樣本。

結果:正確率 0% → **54.5% / 83.3%**,有信心 **0**,靜默錯誤 **0.00%**。

#### 1.5 `2m → 1m`:三條量過的死路(2026-10-25)

這是今天每一份量測裡**唯一**的靜默錯誤來源(舊素材 12 次,新素材 0 次),
歷史上更是 272/273。所以它值得單獨查。

**機制查清楚了。** 把失敗的格子切出來看:三張都是清清楚楚的二萬,而比對器
以 0.70~0.74 對 0.59~0.60 選了 1m。原因是**一萬是二萬的子圖** ——「萬」佔了
牌面大半而且兩者相同,「一」又可以對齊「二」的上橫或下橫。而模板在格子裡
是可以滑動的(刻意的,格線有殘差),滑動正好讓 1m 找到一個很好的位置。
量到的位移是 **dy 中位 15 px**,認對的格子是 2 px —— 訊號完全符合這個解釋。

**但三種修法全是淨負的:**

| 試法 | 結果 |
|---|---|
| 把 `FACE` 掃一遍,看是不是尺寸偏了 | 現行 0.72x0.70 **就是最佳**(零靜默錯誤、有信心張數最高)。假設否定 |
| 收緊搜尋窗(繞**標稱**位置) | 兩邊分數一起崩(0.74 → 0.33)。牌真的不在標稱位置上,偏移超過 10px |
| 釘死在**共識**位置重新評分 | 正確率 95.3% → **56.4%**,有信心 72.2% → 25.6% |
| 共識位置 ±4 / ±8 / ±12 | 71.3% / 78.7% / 86.2%,全部更糟,而且靜默錯誤升到 1.1~1.3% |

最後兩列解釋了為什麼這條路是死的:**格線殘差不是整家一致的平移**,它跟著
格子位置變(透視讓遠端的格子偏移不同)。逐格滑動不是浪費,是在補每一格
各自不同的殘差 —— 而那個自由度正是 95.3% 的來源。半徑越大越接近現行值,
單調,沒有中間的甜點。

**下次不要再試這三個。** 要動這個混淆,得從別的地方下手(例如只對
「候選是同一個數字系列的鄰居」時加一道專門的覆核),而且要先證明它不會
動到那 95.3%。

#### 1.6 棄權**不會**被時間解決(2026-10-25)

這一條推翻了一個本來寫在很多地方的假設。

`tracker` 層的設計寫著「讀不出來的那張**延後**,不是放棄 —— 牌還在桌上」。
聽起來顯然成立,所以從來沒量過。量了之後:

| 取樣 | 觀察次數 | 補上的未知 |
|---|---|---|
| 每 8 幀 | 572 | 3 |
| 每 4 幀 | 1141 | 3 |
| 每 2 幀 | 2280 | 3 |

觀察次數翻了四倍,補上的**一個都沒有多**。未知率三次都是 39.2%。

原因想通了就很明顯:**牌河的牌是不動的**。同一塊像素再讀一百次還是同一個
答案 —— 棄權不是每幀隨機的雜訊,是那張牌在那個位置的確定性質。

這跟手牌完全不同,而那正是假設的來源:手牌會移動、會 hover、會被摸打動畫
改變,所以「等下一幀」真的有用。牌河沒有這個性質。

**後果:** 門檻掃描裡那 25% 的棄權成本**不可能靠多看幾眼拿回來**。要降低它
只有三條路 —— 放寬門檻(換靜默錯誤)、改善那些格子的辨識、或是接受它並讓
下游處理未知。目前走第三條(讀不到的牌當危險處理)。

#### 1.7 赤五不是「另一張牌」(2026-10-25)

把棄權拆開看卡在哪一關(舊素材 5388 格):

| | 佔比 |
|---|---|
| 有信心 | 70.0% |
| 差距小 | 13.3% |
| 分數低＋差距小 | 9.1% |
| 分數低 | 6.9% |

「只卡在差距」的那 719 格裡,次高分是**贏家自己的赤五版本**的有 93 格
(12.9%)。那根本不是歧義:`0m` 與 `5m` 在振聽與筋裡完全等價,而牌河的
正確率本來就是用 `normalize_red` 之後比的。

`Match.margin` 問的是「**有沒有別的牌**也一樣像」,而 `0m` 不是別的牌。
所以 `classify()` 加了 `merge_red`,挑次高分時跳過贏家自己的紅版本,
牌河那條路打開(和牌算符要知道紅不紅,那裡不要開)。

這不是新發明 —— 手牌的 `MIN_MARGIN` 取 0.04 的理由寫著「實測最薄的是普通五
vs 赤五的 0.084」,也就是那條路**早就**在用放寬門檻的方式容納同一件事。
牌河的門檻是 0.10,剛好把它卡死。`merge_red` 是同一件事的正確做法:
不必為它放寬門檻。

| | 有信心 | 靜默錯誤 | 正確率 |
|---|---|---|---|
| 舊素材 | 3608 → **3701** | 0.28% → 0.27% | 95.9%(未動) |
| 新素材 | 999 → **1008** | 0.00% → 0.00% | 94.9%(未動) |

+93 正好等於量到的紅版本格數。零新增的靜默錯誤 —— 新進來的那些格子答案
是 `5m` 或 `0m`,正規化之後都對,所以這是由構造保證的,不是運氣。

剩下的差距小大多是真的混淆:`1m↔2m`、`1m↔4m`、`9s↔7s`、`2m↔3m`、
`8m↔1m`、`6p↔8p`。見 §1.5 —— 那條路今天試過四種修法,全是淨負。

#### 2. `Dahai` —— 把「牌河的狀態」變成「捨牌的事件」(中)

牌河辨識回的是**一條河現在有哪些牌**,MJAI 要的是**誰剛打了什麼**。
中間差一個變化偵測,而它有三個坑:

* **鳴牌會讓河縮短並往前遞補。** 雀魂不留空位 —— 被鳴走那一格空出來,
  後面的牌整排往前移(見 `mia/mjai/table.py` 的 `Player.visible_river`)。
  天真的 diff 會把整排錯位讀成一連串捨牌。
* **一幀之間可能發生不只一件事**(掉幀、動畫),順序要補出來。
* **立直橫放牌**會撐開格線,見上一條。

#### 3. 副露事件(難,但也許不是當初那個難法)

`decisions.md` 第五節記著一次失敗:上家與下家的副露是斜的,而他們的暗手牌是
一整排橘色牌背 —— **與斜面同色**,四張參考圖全部只回傳一個合併的區塊。

那個結論對**當時的問法**成立:從一張靜態圖裡把副露區切成一組一組。

但 MJAI 要的是事件,而已知的約束強得多:

* 被鳴的那張 (`pai`) **就是上一個 `Dahai` 的牌** —— 不必從畫面認。
* `target` 就是上一個打牌的人。
* 只剩 `consumed`(他自己拿出來的兩三張)要認,而那幾張是**正面朝上**的。
* 吃 / 碰 / 槓由張數與來源方向區分。

**這不等於它會成功。** 只是當初那個「切不開」的證據不直接適用,
要先做可行性實驗,不要當成已解決。

#### 3.1 可行性:看過圖了(2026-10-27)

拿 `20261024-123746` 裡有副露的幀直接看。**結論:當初那個失敗不適用,
但換來了三個新的麻煩,而且素材嚴重不足。**

##### 好消息:顏色根本不是問題

`decisions.md` 第五節那次失敗是「顏色分割 + 從靜態圖切區塊」:副露的斜面
與暗手牌的橘色牌背同色,四張參考圖合併成一塊。

但畫面上**副露是正面朝上的白牌,暗手牌是一整排橘色牌背** —— 正面與背面
在顏色上分得非常開。那次失敗是敗在「用顏色去切邊界」這個方法,不是敗在
「副露看不見」。我們也不打算用顏色切:

##### 結構跟牌河一模一樣

每一家的副露在**固定的角落**,沿著桌邊長:

| 視角位置 | 副露在哪 | 本次素材 |
|---|---|---|
| 自己 | 右下角,往左長 | 2 次 |
| 下家 | 右側,往上長 | **0 次** |
| 對家 | 左上角,往右長 | 3 次 |
| 上家 | 左側,往下長 | 4 次 |

所以 `DEFAULT_CORNERS` 那一套(四角 + 單應變換攤平 + 格線)**可以直接沿用**,
不必發明新方法。

##### 三個新麻煩

1. **副露緊鄰牌山,而牌山也是牌。** 牌河沒有這個問題(牌河在桌子中間,
   四周是空桌布)。牌山還會隨著局的進行**變短**,所以「這一格有沒有牌」
   在副露區不等於「這裡有副露」。
2. **立繪會整片蓋住。** 實測 t=300s 那一幀,立直動畫斜著蓋掉半個畫面,
   自己那區全沒了。牌河遇過同樣的事(§1.1 第 6 條),但副露只有 0~4 組,
   少看到一組就是少一組 —— 不像牌河有連續性可以自我檢查。
3. **組數會變但不會減。** 這一點反而是好消息,與寶牌同一個模式
   (見 §4.1):同一局之內只增不減,短暫的消失直接忽略。

##### 素材不夠,這是現在最大的限制

一整場只有 **9 次鳴牌**,而且:

* **下家 0 次** —— 四個視角位置裡有一個完全沒有樣本。
* **槓 0 次** —— 明槓、暗槓、加槓三種全部沒驗過。這與 §4.1 的槓寶是
  同一個洞:兩份錄影都沒有人槓。

**所以第 6 步在補素材之前做不完。** 可以先做的是下面這個分階段。

##### 分兩階段,第一階段就有用

| | 要什麼 | 換到什麼 |
|---|---|---|
| **一、只數張數** | 副露區有幾張正面朝上的牌 | 鳴牌的**直接證據**(見 §5.1,現在是靠「連兩次才採信」猜的)、副露組數、「3副露」威脅標籤 |
| **二、認牌面** | 每一張是什麼 | 「壁」的張數 |

第一階段不必認牌,所以躲得過上面第 1 個麻煩的大部分 —— 牌山是**背面**,
副露是**正面**,只要分得出正反就夠。而它直接消掉 `RiverWatcher` 現在那個
推論:鳴牌之所以要靠連續性猜,就是因為看不到副露區。

#### 3.2 第一階段:上家量完了(2026-10-27)

程式碼:`mia/vision/tiles/melds.py`。攤平成一條 1x13 的帶子,每一格只問
`is_face_up` —— 那支本來就是牌河與寶牌共用的,桌布、牌背、翻開的牌各由
一個顏色維度分開。**第一階段不認牌面,所以格子不必擺正**,四個角只要框住
帶子、沿長度切得開就夠。

整份錄影逐幀對分:

| 家 | 可評分 | 張數對 | 整家棄權 | **讀錯** |
|---|---|---|---|---|
| 上家 | 3705 | **95.92%** | 3.83% | 0.24% |
| 對家 | 3732 | **95.26%** | 4.42% | 0.32% |

**讀錯的那幾次全部是「讀太多」,兩家都是 0.00% 讀太少。** 多算副露會高估
威脅,方向符合第七節的要求。

##### 角點是搜出來的,而這次有真值

`river.DEFAULT_CORNERS` 當初是在**沒有真值**的情況下搜的,目標只能是
「有牌的格數 + 有信心的格數」。這裡條件好得多:封包逐秒都說得出每一家
有幾張副露牌,所以目標直接就是「讀出來的張數等於真值」。

兩個坑:

1. **框的是「可能的全長」,不是「現在有多長」。** 第一次框住現有那 9 張
   的兩端,13 個格子全部落在那 9 張牌裡,讀出來 13/13。
2. **目標函數要分開看「0 張」與「有副露」。** 不分的話退化解會贏 ——
   一個框到桌布上的四邊形永遠讀 0,而大部分幀的真值就是 0。

搜出來只比目測好 0.2 個百分點(上家 95.73% → 95.92%),所以目測的起點
本來就不差。**搜的價值在於不必再目測另外幾家。**

##### 缺的兩家

* **下家**:素材 0 次鳴牌,一張樣本都沒有。**搜不了,只能補素材。**
* **自己**:副露緊貼著自己的手牌,而**手牌也是正面朝上的** ——
  `is_face_up` 分不開,搜出來的分數接近 0(連「沒有副露」的幀都讀錯,
  因為 13 格的帶子一路穿過手牌)。牌山那個麻煩躲得過(牌山是背面),
  這個躲不過。

  **但自己這一家正好是最不需要的。** 放銃分析從不對自己算危險,所以自己
  的副露只餵「壁」,而壁用的 `TableTracker.visible` 本來就含自己的手牌。
  進了副露的牌是從手牌出去的,少算會讓 `remaining` 偏高,於是「四張全見」
  的排除不觸發、那個待牌仍然算危險 —— **方向是保守的**。

所以第一階段對**三個對手**需要三家,現在有兩家。缺的那一家缺的是素材,
不是方法。

#### 3.3 素材要從牌譜來,不是從機器人來

跟機器人打**錄不到想要的東西**。他們會不會槓、下家會不會鳴,那是運氣 ——
實測整場 `20261024-123746` 九次鳴牌,下家 0 次、槓 0 次。再錄一場也只是
再賭一次。

牌譜是**挑**的。而且雀魂的牌譜**可以換視角** —— 同一場看四次就有四個視角,
某個人鳴牌,從他下家看就是上家鳴牌、從他對家看就是對家鳴牌。
「下家沒有樣本」這個問題直接消失,還順便給了一個現在拿不到的東西:
**同一次鳴牌的四個視角**,可以互相驗證角點。

牌譜畫面本身已經驗過了:`ui/panel/tablerect.py` 的自動校正就是在牌譜畫面上
量的(差 18 px,微調之後四家全部連續),所以牌桌幾何與實戰一致,
現有的 ROI 與四角全部適用。

##### 代價:時間基準沒了

整場紀錄是 `fetchGameRecord` 在**一開始一次**送來的,而畫面要幾分鐘才演完。
即時對局那條路靠 `wall` 把每一幀配上那一刻的封包真值,牌譜沒有這個東西。

所以 `tools/capture.py --replay` 會:不等 `end_game`(那個事件不會來),
也不跑對齊檢查(它必然回「0 個牌河狀態」,看起來像素材錄壞了)。

| 要做什麼 | 牌譜現在夠不夠 |
|---|---|
| 校正角點(下家、槓) | **夠** —— 上家只用了一張圖 |
| 看槓在畫面上怎麼排 | **夠** —— `COLUMNS = 13` 是推論的,沒看過實物 |
| 量 95.x% 那種準確率 | 不夠,要先做對齊 |

##### 對齊要怎麼做(做了,見 §3.4)

`to_mjai.py` 的 `_on_game_restore` 已經在處理「一整批 actions」了,而且註明
那些動作**沒有經過 XOR 混淆** —— 牌譜是同一個形狀,轉 MJAI 那段幾乎原樣
能用。缺的只有時間。

可行的辦法是**單調匹配**:牌河張數在一局之內只增不減,每一個 `dahai` 正好
加一。CV 逐幀讀得出那個總數,封包給得出那個序列,兩邊做一次單調對齊就能
把每一幀配上一個動作索引。局的邊界(已經偵測得到,見 §4.1)是現成的錨點。

#### 3.4 單調對齊:做了,而且它看到了舊評分看不到的東西(2026-10-29)

程式碼:`mia/eval/sequence.py`;`mia/eval/rivers.py` 拆出 `read_rivers`
(只讀不配答案)。

##### 先在有答案的素材上驗

存檔(`session.py`),所以有變化的幀幾乎全是動畫中途** —— 而 `stable_at`
正好跳過動畫。兩邊評的是不同的幀,數字不能比。

改成全部 4533 幀(沒變化的幀沿用寫出那張影像的幀的讀取結果)才對得上。

##### 但評的範圍變大之後,靜默錯誤不是 0

單調對齊對**每一幀**都給得出答案,包括 `stable_at` 拒絕回答的那些
(狀態維持不到 1 秒的、局尾的)。用同一批讀取、只算採用的幀:

| 評哪些幀 | 幀數 | 每張牌 | 靜默錯誤 |
|---|---|---|---|
| 真時間 `stable_at`(舊的評法) | 1185 | 94.6% | **0.00%** |
| 單調對齊,畫面靜止 ≥ 1.2 秒 | 1281 | 94.5% | 0.14% |
| 單調對齊,畫面靜止 ≥ 0.8 秒 | 1510 | 94.3% | 0.15% |
| 單調對齊,全部幀(依時間加權) | 4533 | 93.6% | **0.50%** |
| 單調對齊,不重複影像 | 1138 | — | **1.02%** |

**「靜默錯誤 0.19%」那個數字是在一個偏向慢節奏、偏向局中段的母體上量的。**
`stable_at` 要求狀態維持 1 秒,而電腦對手出牌快的時候狀態每 0.5 秒就變一次,
局尾最後一張打出去不到一秒就結算 —— 那些幀從來沒被評過。

逐一查過,三類錯誤全部是**真的認錯**(對齊在那些幀上與真值一致,畫面也
看過了),不是對齊配錯:

| 錯 | 次數(不重複影像) | 位置 | 原因 |
|---|---|---|---|
| 二萬 → 一萬 | 107 | 自己第 9、10 格 | **模板被壓扁了**,見 §3.5 |
| 5s → 2s | 18 | 上家第 12 格 | **上家第六欄被四邊形切掉一截**,只剩半張牌 |
| 各種 → 白 | 11 | 對家第 7~11 格 | 待查,短暫出現 |

切邊的證據很直接:上家第 6 格整場 0 次有信心、503 次棄權;**對家第 6 格
也是 0 次有信心、496 次棄權**。第一列第六張被切掉時剛好棄權了,第二列
第六張只剩半張時卻讀成了別的牌。

**二萬讀成一萬是最危險的一類。** 發生在對手的牌河時,系統會說一萬是現物,
而對手根本沒打過一萬 —— 正是 §5.1 那種無症狀的假現物。這次只發生在自己
那一家,是運氣。

##### 接進重播工具:結算畫面差點造出 555 張假現物

`tools/replay_table.py --sequence` 讓重播工具改用單調對齊當答案。第一次跑:
**假現物 555(9.89%)、多了格子 767**,四家平均分布 —— 不可能是真的。

原因是對齊裡沒有「結算」這一步。結算面板蓋住的那幾家讀成 0 張而且連續,
與**下一局的空桌**完全吻合,於是結算畫面被配進了下一局;tracker 這時正確地
還握著上一局的河,每一張都被算成假現物。我的驗證只看「真時間有答案的幀」,
結算期間真時間的答案是邊界,所以那段從沒驗過。

修法是把 §4.1 那條規則搬進對齊:封包的局邊界也是序列裡的一步(代價等於
「四家都空」,但讀不到的家不扣分),而新局的空桌要**四家都讀得到**,每少一家
加罰一份。這與 `KyokuWatcher` 宣告新局的條件一致,兩邊因此同步。
結算期間被給答案的幀 363 → 153(剩下的是和了封包已到、面板還沒蓋上的那一兩秒,
畫面上牌河確實還在),開局前 50 → 0。

修完之後(還是舊讀法)重播的結果:**假現物 20,全部是真的** —— 自己的二萬
讀成一萬 14 輪、上家切邊的 5s 讀成 2s 6 輪。舊的尺報 0,因為兩張都發生在
局尾、狀態不到 1 秒,而 tracker 裡的錯牌一直留到換局,一次都沒被評到。
**舊的尺在這份素材上只評得到 447 輪裡的 114 輪。**

§3.5 修好讀法之後:

| 單調對齊當答案,379 輪 | 舊讀法 | 新讀法 |
|---|---|---|
| 格線:對 / 棄權 / **錯** | 63.4% / 36.1% / **0.5%** | 79.5% / 20.5% / **0.0%** |
| **假現物** | **20** | **0** |
| 立直 | 2 / 2 | 2 / 2 |
| 一輪:中位 / 最久 | 23 / 910 ms | 12 / 554 ms |

##### 這對牌譜素材的意義

牌譜素材**只能**用單調對齊,而它評的範圍比舊評法廣。所以往後的數字要並列
兩種範圍,不然牌譜素材的數字看起來會「比即時素材差」—— 那不是素材變差,
是量得比較誠實。不靠真值的「畫面靜止 ≥ x 秒」可以當成 `stable_at` 的
替代,讓兩種素材在同一個範圍上比。

#### 3.5 二萬讀成一萬:模板的高度從一開始就錯了(2026-10-29)

程式碼:`mia/vision/tiles/river.py` 的 `FACE`、`SEARCH_BELOW`、`search_window()`。

##### 不是座位、不是素材,是系統性的

§3.4 的單調對齊讓整場每一幀都評得到分,於是二萬的問題第一次看清楚:

* 兩份素材、四家都有。校正素材上自己第 8 格 57 次、下家第 16 格 49 次。
* **新素材上二萬一次都沒認對過**(790 格:對 0%、有信心地讀成一萬 13.5%)。
* 兩份合計,二萬讀成一萬佔了全部靜默錯誤的八成以上。

`CHECK_FACE_HEIGHT` 的註解早就記著「二萬在 0.70 時有三分之二被讀成一萬、
錯的分數還更高」與「最佳落點常常頂在格子下緣」。當時的解法是兩個尺度
一致才表態 —— 但這些幀上**兩個尺度都說一萬**,兩個都太小,一致地錯。

##### 量出來的牌面大小

對每一格,拿**真值那張牌**的模板掃寬 56~88、高 72~112,找分數最高的尺寸
(搜尋窗往下多給 30 像素,讓高的模板放得下):

| 家 | 列 | 最佳寬 | 最佳高 | 落點 y |
|---|---|---|---|---|
| 四家 | 第一列 | 60~64 | 92(對家 97) | **28~34** |
| 四家 | 第二列 | 64~68 | 92(對家 102) | 8~15 |
| 四家 | 第三列 | 68 | 82~97 | 0 |

兩份素材幾乎一樣。**現行模板 65 x 84:寬度對,高度少了 9%。**

落點那一欄解釋了為什麼當初會掃出 84:第一列的牌面頂端在格子下方約 30 像素,
30 + 92 超出格子的 120。掃描時搜尋範圍就是格子本身,高的模板塞不下,
只好選一個塞得下的矮模板。被壓扁 9% 的「二」兩橫間距對不上,一萬那一橫
反而落在中間。

##### 修法:用對的高度,讓搜尋窗往下長

不能把格線整個往下挪:落點每一列不同(30 / 12 / 0),往下挪會讓第三列
反過來被切掉。所以格線不動、有無判斷不動(`_OCCUPANCY_FACE` 維持舊值,
張數判斷沒有問題),只讓**認牌的搜尋窗**往下多看 30 像素,模板自己找落點。

抽樣(二萬、一萬全收,其他牌抽 15%):

| 素材 | 牌 | 現行(對 / 錯) | 64 x 92 + 往下 30(對 / 錯) |
|---|---|---|---|
| 新素材 | 二萬 | 0.0% / **13.54%** | 53.2% / **0.00%** |
| | 一萬 | 19.3% / 0.00% | 99.5% / 0.00% |
| | 其他 | 66.6% / 0.10% | 78.9% / 0.07% |
| 校正素材 | 二萬 | 0.0% / **4.73%** | 38.0% / **2.24%** |
| | 一萬 | 30.9% / 0.00% | 51.4% / 0.00% |
| | 其他 | 75.8% / 0.00% | 83.8% / 0.03% |

**正確率與靜默錯誤同時改善** —— 不是在門檻上用棄權換錯誤,是原本的幾何
設定就錯了。只放大搜尋窗、模板不改(65 x 84 + 往下 30)則二萬毫無改善、
一萬全部變成棄權:兩件事要一起改。

覆核的第二個高度實測已經不擋任何東西(單一尺度與覆核 96 結果相同),
但它不花正確率,而且它當初擋的那一類錯換一份素材可能又出現,所以留著,
比例維持 0.73 / 0.70。

##### 全量:同一套評分、同一批幀,只換讀法

`stable_at`(舊的尺),每一幀四家全讀。「舊讀法」是把 `FACE`、
`CHECK_FACE_HEIGHT`、`SEARCH_BELOW` 三個常數換回舊值,其餘程式完全相同。

| | 新素材 舊 → 新 | 校正素材 舊 → 新 |

| 幀 | 1185 | 1921 |
| 靜默錯誤 | 0.00% → 0.00% | **0.24% → 0.17%** |
| 棄權 | 28.2% → **13.6%** | 23.7% → **15.8%** |
| 有信心且對:自己 | 62.3% → 80.8% | 65.2% → 67.9% |
| 　下家 | 74.5% → 91.6% | 62.3% → 85.9% |
| 　對家 | 56.1% → 73.7% | 66.2% → 78.5% |
| 　上家 | 71.5% → 80.1% | 90.7% → 93.8% |

新素材上自己那一家「每張牌」(不看信心的原始標籤)從 97.1% 掉到 92.9%,
變的是**棄權格子的原始標籤**;有信心且對的比例是 62% → 81%,靜默錯誤仍是 0。

**立直宣言牌的偵測**(它的第一、三關也用直放認牌):新素材 42 次判定逐幀

##### 剩下的:第三列

校正素材下家第三列有一張二萬在 24 幀裡讀成一萬,**現行設定下也一樣錯**,
新設定沒有讓它變糟。第三列量到的高度比較矮(82~87),把第三列的模板壓到
82 就消得掉,但第三列的素材太少(每家 13~29 格),而那 24 格很可能是同一張牌。
不為一張牌另外調一個尺寸,記著。

→ 後來查清楚了,**不是高度**,是搜尋窗沒有往上看。見 §3.6。

##### 校正介面刻意不跟著改

`ui/panel/tablerect.py` 用「有信心的比例」判斷牌桌框有沒有框歪。用新的認牌
方式打分的話,上緣偏 0 / +0.2% / +0.5% 的有信心比例是 75% / 78% / 72%,
**平的** —— 搜尋窗往下長,小偏移它自己找得回來。但偏 0.5% 的框上每張牌
正確率是 90.8%,正確的框是 98.0%(多出來的是棄權不是錯誤)。

認牌要「偏一點也讀得對」,校正要「偏一點就看得出來」,兩件事要的相反。
所以校正保留舊的探針(65 x 84、只看格子本身)。改之前與改之後,同一張圖
上緣偏 0 / +0.2% / +0.5% / +1% 的有信心比例**逐位相同**:85% / 75% / 65% / 23%。

(順帶:`_MIN_RIVER_CONFIDENT` 註解裡那張表寫的是 83 / 74 / 63,是更早的
程式量的。而偏 0.5% 現在是 65%,**剛好貼著 0.65 的門檻** —— 這是改之前
就這樣的,不是這次造成的,但這條防線比註解寫的薄。)

#### 3.6 角點重搜、第三列被切頂(2026-10-30)

##### 起點:新素材上家第六欄整場 0 次有信心

用 §3.4 的單調對齊當答案逐格統計,新素材(123746)上家第 6 格 **0 次有信心、
503 次棄權**,對家第一列的牌頂被四邊形切掉。舊素材(110639)上同一格有
1123 次有信心。

差別在畫布:110639 是 2536x1434(長寬比 1.7685,說明欄寫著「中途縮放」),
123746 是精確的 16:9。角點是在 110639 的**一幀**上搜的,吸收了那份素材
特有的偏移。只拿 123746 重搜上家,123746 從 361 升到 440,但 110639 從 667
掉到 658 —— 兩份素材要的角點不一樣,只配合一份等於換一份過擬合。

所以改成**兩份一起搜**:各取約 60 幀(再補一批河排到第三列的幀,不然目標
函數看不到第三列),目標是兩份的「有信心且對 − 20 x 有信心卻錯 − 5 x 張數
不對」總和,每一步都看兩份各自有沒有變差。

##### 第三列被切頂:二萬讀成一萬的真正原因

第一輪重搜之後,第一、二列大幅進步,第三列卻崩了(自己那家 44% → 5%)。
攤平圖一看就知道:第三列的牌面頂端在格子上緣**之上**。§3.5 量到的落點是
第一列 30、第二列 12、第三列 **0** —— 貼著邊,角點一動就變負的,而搜尋窗
只往下長,模板滑不上去。

`SEARCH_ABOVE = 8`:搜尋窗往上多看 8 像素。上一列的牌在 120 像素外,對不到。

**這也才是 §3.5 那張二萬的真正原因。** 同一格(110639 幀 8696):

| | 模板高 92 | 模板高 80 |
|---|---|---|
| 不往上看 | 一萬 0.63 / 差距 0.18(**有信心的錯**) | 一萬 0.68 / 0.07(棄權) |
| 往上 8 像素 | **二萬 0.84 / 0.14** | 一萬 0.68 / 0.07(棄權) |

「第三列牌面比較矮,改成 80」那個方案(這一輪一度實作了)讓錯誤消失,
**只是因為它把有信心的一萬變成沒信心的一萬** —— 從來沒讀對過。逐家掃第三列
的最佳高度,四家給出 88 / 96 / 96 / 92,每家只有 8~11 張不同的牌,是雜訊。
所以第三列的特殊高度整個拿掉,`face_size` 維持不分列。

##### 對家刻意不動

對家搜出來的角點讓第一、二列從 72% / 56% 升到 91% / 65%。但它改變了攤平後

|---|---|---|
| 舊角點 | 268 | 52 |
| 對家新角點 | **0** | **320** |

只動垂直方向也一樣找不到。漏掉立直就是把危險牌當安全,正確率換不回來,
所以對家維持舊角點。要動對家,得先讓宣言牌的比對不依賴攤平後的比例。

(宣言牌比對的窗也改成與 `search_window` 一樣上下延伸,理由同上。兩份素材
對真值逐幀比,命中 / 漏 / 誤判與 HEAD **完全相同**。)

##### 重播:過場的白光在即時路徑上會留下來

逐幀評分裡「→ 白」只是幾幀的事,但重播(`tools/replay_table.py --sequence`)
一跑,110639 出現 42 輪假現物,**全部是白**。即時路徑每一格只認一次、認完就
快取,一次讀錯就一直留著。兩種來法:

1. **白光讓空格看起來有牌**,一口氣多出 2 / 3 / 5 / 7 格,讀成有信心的白,
   當成新捨牌發給 tracker。動畫結束後河變短,那被當成鳴牌 —— 發過的打牌
   不會收回。從來沒有只多 1 格的。
2. **真的打牌剛好遇上白光**:上家一張一索在白光掃過的那一刻打出來,河只多
   一格,讀成白。

對應的兩道防線:

##### 認錯是怎麼一個一個消掉的

三種)就整組當未知 —— 不知道哪一張錯,就一張都不信。

##### 認不全的,用規則補

只做**一定成立**的推論:

* **兩張數牌差 2,中間那張就知道了**(6 筒 + 8 筒 → 6 7 8 筒);差 1 而碰到
  端點也只有一種(1 2 → 1 2 3、8 9 → 7 8 9)。CPU 對局上家吃 1 2 3 萬,
  認到的是 1 萬、2 萬。
* **同一種牌在兩個位置都認到,就是碰**(吃不會有兩張一樣的)。但橫放的牌比
  直的寬,同一張會被相鄰兩框各認一次 —— 量過:這種重複最遠相距 50,碰的
  兩張不同的牌最近 100,門檻取 100。順子裡出現這種重複就整組作廢。

整組完整的從 27 組變 **34 / 48**(牌譜)、**6 / 7**(CPU 對局),以多重集合
比對答案(記成三張 6 萬,答案就得真的是三張 6 萬)仍然 **0 錯**。

想法是鳴牌確認那一刻牌可能還在滑,沒認全的組隔幾秒拿新畫面再認、把結果
併起來。兩場牌譜八個視角,每組認到五次:**一組都沒有多認出來**。漏的是系統性
的(上家太糊、跨框的誤讀讓整組作廢),不是時機 —— `MeldWatcher` 本來就等
長度連兩次一樣才確認,那時牌早就停了。撤掉,不留沒有效果的機制。

##### 骨架:由捨牌序列驅動

第一版想用「輪到誰 + 等副露確認」的狀態機,失敗了:副露確認比捨牌晚 2 ~ 4 秒,
到的時候順序早就過去了。

轉折是:**每張捨牌本身就帶著座位** —— 出現在誰的河裡就是誰打的。所以到達順序
就是打牌順序,同一輪的並列才用輪替決定。兩張捨牌之間發生什麼,由座位與余牌推。
`unseen` 是「余牌顯示摸過、事件流還沒交代」的摸牌數:

| `a` 打完接著 `s` 打 | `unseen` | 中間發生的事 |
|---|---|---|
| `s` 是下家 | 1 以上 | 正常摸打 |
| `s` 是下家 | 0,有副露 | `s` 吃 |
| `s` 是下家 | 2,有副露 | 暗槓(摸、槓、嶺上) |
| `s` 不是下家 | 0 | `s` 鳴了 `a` 的牌 |
| `s` 不是下家 | 1 以上 | 中間有人摸打,**那張牌一打出就被鳴走,河裡從沒出現過** |

最後一列是每秒讀一次的盲點,也只有余牌補得回來。

##### 門檻互換是假問題

一開始拿「兩張捨牌之間余牌少了幾張」當證據,怎麼調都是互換:減 1 就補的話
7 局對但多補,減 2 才補的話 6 局對但漏補。原因是素材是 CPU 對局,**每個動作只隔
約 0.5 秒**,下家的摸牌常常落在同一輪,多算一張。

本來以為要提高余牌的取樣率(讀一次只要 0.13 毫秒,很便宜),但其實不用:

1. **看上一輪的余牌。** 牌出現在 `t - 1` 與 `t` 輪之間,而下家的摸牌至少再晚半秒,
   所以第 `t - 1` 輪的余牌不會混進下家的摸牌。
2. **比累積值不比差值。** `70 - 已發出的摸牌數` 與余牌比,誤差不會每一步重新開始。
3. **正常摸打時吸收差額。** 加槓看不見,但嶺上會讓余牌多減一張,不吸收的話之後
   每次跳家都多補一張。

##### 不是每張讀到的牌都是真的

和了之後結算畫面會被讀成一排 `?`(實測一局最多多 3 張)。規則:**真的捨牌一定有
摸牌或副露**。等了 4 輪兩樣都沒有,就丟掉。跳家因此也要等副露確認。

丟掉有連鎖風險:誤丟一張真牌,`last` 就停住,之後每張都變成「跳家且沒有副露」,
整局後面一路被丟(實測一局少 5 張)。所以跳家沒副露但**余牌有減**時不丟,補上
漏看的再接回去。

##### 數字(兩份錄影 12 局,線上跑、不看未來,對封包)

| 評分範圍 | 封包的事件有排出來 | 排出的事件裡對不上的 |
|---|---|---|
| 含結算畫面的假牌 | **1116 / 1143(97.6%)** | 8 / 1124 |

一致率比不丟假牌時略低(98.6%),差在局尾最後一兩張 —— 放銃那張打出就被結算
蓋掉。局一結束那張就不影響任何後續狀態,而多發一個假事件會。取捨是對的。

素材是最嚴苛的情況(每 0.5 秒一個動作、每秒讀一次)。真人對局應該幾乎不用等副露,
但還沒有素材量。

##### 量的時候踩到的

* **別用 `difflib` 比這種序列。** 輪替高度重複,少對齊一格就把整段算成錯,
  開局看起來一團亂其實是尺的問題。逐張比才看得出真正的錯在哪。
* **逐張比也有連鎖:** 中間少一張,後面的索引全部位移,要分開看。
* **開局訊號要四家都連續,讀牌只看單家** —— 第一張牌遇上別家不連續就被收下、
  下一輪重設、再發一次。已修:局還沒開始就不讀牌河。
* **`Dahai` 只送認得出來的牌**,約 14% 的 `?` 不進 tracker、也不重認。放銃分析
  無所謂,Mortal 不行。

##### 副露是事件流裡最可靠的訊號

兩份錄影 29 次鳴牌(含自己)全抓到,多記 0,延遲中位 2 ~ 3 秒、最久 4.1 秒。

準確率看不出 Mortal 在不在乎某個錯,所以直接比決定:把封包的事件流與畫面組的事件流
餵給同一份權重,逐手比「自己摸牌之後的第一選擇」。

| 素材 | 自己摸牌的決策 | 排到 | 局末 | 線上排到 | 線上相同 | 引擎報錯 |
|---|---|---|---|---|---|---|
| 真人半莊(13 局) | 150 | 150 | 143(95.3%) | 150 | **142(94.7%)** | 0 |
| `20261024-123746`(4 局) | 47 | 47 | 43(91.5%) | 46 | **41(89.1%)** | 0 |
| `20260801-110639`(8 局) | 89 | 77 | 65(84.4%) | 72 | **59(81.9%)** | 0 |

* **局末**:用整局結束時知道的一切。
* **線上**:只用摸牌那一刻已經排出來的東西,這才是使用者看到的。
* 半莊本來 155 手,錄影提早結束,有 5 手沒有畫面。
* 鳴牌的決策(別家打牌時問要不要鳴):47 / 50、17 / 20、30 / 42。
* 上表的副露牌面是立刻認好的,比實際樂觀,所以還要下面那張。

槓的素材(線上,引擎報錯 0):四槓子四個視角 35 手相同 34 手,兩組槓四個視角 108 手
相同 99 手(91.7%)。大明槓由副露長度分辨,碰與吃是 1.0 個組長,槓至少 1.13。

**真實時間**:`20261024-123746` 照錄影的速度播給真正的 `VisionAdviceWorker`,有真的
工作執行緒、真的 Mortal 子程序,副露牌面也真的要等 4 ~ 5 秒。

| | 給了建議 | 與封包相同 | 打牌之前就到 | 延遲中位 / p90 / 最久 | 重播 |
|---|---|---|---|---|---|
| 牌桌一秒醒一次 | 44 / 47 | 39 | 19 | 1.67 / 3.62 / 4.29 秒 | 26 次 |
| **手牌一變就醒** | 40 / 47 | **38(95.0%)** | **31** | **1.17 / 2.81 / 3.47 秒** | 18 次 |

「打牌之前」是相對 CPU 的節奏,它一手只想 1.4 秒。真人想得比較久。沒給建議的手數變多了
(3 → 7),一部分是量法:測試每 0.25 秒才收一次郵箱,而郵箱只留最新的一份,鳴牌的提問
會蓋掉切牌建議。實際的 UI 每 0.1 秒收一次,但這一點沒有另外量。

**這些數字的限制,要一起講:**

1. **半莊是一步一步按的牌譜**,沒有真實時間壓力。兩份即時素材是 CPU 對局,每 0.5
   秒一個動作而每秒讀一次,是最嚴苛的情況。**真人即時對局的節奏介於兩者之間,還沒量過。**
2. **還沒有接過真的遊戲視窗。** 真實時間那張表是錄影播出來的,手牌讀數是預先讀好、
   每 0.25 秒一筆的,不是 `VisionWorker` 那條「畫面停下來才認」的路。
3. 「與封包相同」量的是**一致**,不是打得好不好。Mortal 不確定的局面本來就會換答案,
   一致率到不了 100%。

##### 每一輪重算,不是一路累加

事件流發出去就收不回來,而畫面的知識是會變多的:副露的牌面晚四五秒、立直要點數變了才
知道、立直那一列要等橫放牌找到才對得準。所以 `compose()` 是純函式,每一輪從
「到目前為止知道的一切」算出**一整局**的串流。新的流接得上舊的就送尾巴,接不上就從
`start_game` 重播這一局。

這也解決了第五張的問題:libriichi 不收同一種牌的第五張,而猜錯的牌佔掉名額的話,之後
真的那一張就違規了。一路累加的話不知道「之後」,整局重算才能先替確定的牌保留名額。

送出去之前還要自己驗過一次:引擎報錯一次,`EngineGroup` 就把它整場移除。不合法的地方
就停在那裡,等更多資訊來改寫。

##### 自己的動作走在 `TurnTracker` 前面

`TurnTracker` 是捨牌驅動的,打出去才排得出那一手,但 Mortal 要在打之前回答。所以手牌一
變成 14 張,摸牌就接在串流尾巴上;之後 `TurnTracker` 排出同一步時內容一樣。

`HandWatcher` 比前後兩副手牌:半莊 307 個動作對 305 個(兩個都是莊家第一手,分不出哪張是
摸的,不影響手牌)。

##### 赤五看顏色,不認圖案

赤五與普通五形狀一樣,普通五有黑字、黑圈或綠條,赤五整張紅。模板比對看的是圖案,差距很薄;
牌面的墨水有多少是紅的,直接分得開(半莊 13 局的牌河逐格量,數字是紅墨比例):

| 花色 | 普通五最高 | 赤五最低 | 門檻 |
|---|---|---|---|
| 萬 | 0.60 | 0.86 | 0.73 |
| 筒 | 0.16 | 0.86 | 0.50 |
| 索 | 0.33 | 0.59 | 0.46 |

三件事用同一個訊號:

1. **認出是五的格子,赤不赤由顏色決定**,不看模板分數。
2. **認不出來的格子每輪看一次顏色。** 每一格只認一次,而剛打出來的牌還在動畫裡:一張赤 5 筒
   第一幀被猜成白,之後不會重認。其他牌沒有這麼便宜的訊號(一格 14 微秒),整張紅的再拿
   赤五與中認一次。
3. **有無判斷。** 赤 5 筒整張紅,中位色相落在牌背上,被當成背面朝上,河中間一個洞,整家判成
   不連續:半莊東一局對家因此斷斷續續丟了 40 幾輪。只看「紙夠多」會把動畫中的牌與半張牌背
   一起放行(B 份有三局的事件流變差),要紙夠多**而且**整張紅。

副露更難:牌面只認得到一部分,赤五常常就是認不到的那一張。但顏色不必認牌。掃一張牌大的框,
看最紅的那一框,每組 16 毫秒。**框的兩半都要有紅**:萬字本來就是紅的,框滑到只蓋住下半張
時,一萬到九萬都能到 0.87。

| 分數 | 組數 | 範圍 |
|---|---|---|
| 真的赤五(5 索 3 組、5 萬 1 組) | 4 | 0.79 ~ 0.88 |
| 其他萬子 | | 最高 0.75 |
| 其他筒子 | | 最高 0.51 |
| 其他索子 | | 最高 0.46 |

門檻依花色取 0.77、0.65、0.62。花色由事件流推,不靠顏色。槓不用看畫面:四張五一定有一張赤。

**樣本不夠的地方:** 副露裡的赤 5 筒沒有真實樣本,上家、對家的赤五也沒有。把真實畫面裡的普通五
改成紅色,各座位最低 0.79,上家的萬子最緊。這只是壓力測試,不是驗證。萬子的間距也比另外
兩色薄:框對齊差一點,分數會差 0.015。

赤牌對 Mortal 第一選擇的影響量過:修正前後所有素材的決策數字完全相同。這是把局面補正確,
不是提高一致率。

**這次比對抓到封包這條路的錯。** 寶牌欄位原本只看嶺上摸牌那一則,但加槓與大明槓的新指示牌
其實在**下一個動作**:打牌那一則,或嶺上摸到又開槓的那一則。四份牌譜與一場即時封包都一樣。
所以網頁版封包模式漏掉了這些寶牌,畫面這條路反而是對的。測試用的是當初想像的訊息形狀,才沒
抓到,現在加上實際的形狀。修正後槓的素材重跑,決策數字與修正前相同。

##### 真人對局才有的問題

CPU 打得快又整齊,以下每一件在 CPU 素材都看不出來:

1. **鳴完想很久。** 副露紀錄原本只等捨牌前 4 輪,CPU 馬上打,真人想十幾秒,副露全被當成
   太舊。現在只要在上一張捨牌之後都算。
2. **鳴完打牌、馬上輪到自己。** 副露還沒確認就得排出來。跳家、打之前沒人摸、之後只減了
   下一家的那一張,只可能是鳴牌,不必等副露。被跳過的那幾家自己有副露時不算,那才是跳家的
   原因。
3. **摸切快到手牌沒讀到 14 張。** 立直後的自動摸切一定會這樣。河裡多一張就補上,那張手上
   也有時多等兩輪,因為多半是手牌讀數還沒到。
4. **鳴完馬上打,手牌一次少三張。** 兩張一樣加一張別的是碰完打牌,不是大明槓。
5. **打牌的特效。** 角色的手與花瓣飄過摸牌那格,被讀成一張低信心的牌。那格沒把握就不收;
   其他格沒把握,要畫面靜止一秒才收(`_STILL_FRAMES`)。動畫中的誤讀很快就過了,應該擋;
   一直認不好的牌擋住的話手牌會凍結,所以是等,不是丟。

與真人無關、之前就錯的三件:

* **余牌的差額全算給一家。** 河晚讀到時差額裡有下一家的摸牌,多算之後每張牌都像沒人摸,
  真的捨牌被丟掉。
* **對家模板太矮。** 對家離鏡頭最遠,攤平時被拉長。高度 92 → 104,平均分數網頁版 0.76 →
  0.82、Steam 0.67 → 0.80。
* **大廳被讀成副露。** 開局前的畫面讀到假的長度,開局又不重設。Steam 上自己第一組的開頭空白
  比網頁版大 0.46 格,碰也會量成槓,現在扣掉。

##### 副露逐組對封包

   判斷副露寬度的分支排在後面,永遠走不到。現在有寬度是槓的副露時先走槓。

##### 手牌對不上時不能卡死

實打回報兩種卡住,都在 `HandWatcher`,而且都是**畫面沒變就不重讀**造成的:原本的規則靠「同一副
手牌連讀三次」,實戰裡幾乎不會發生,重播會反覆餵才沒看出來。

**自己加槓。** 加槓加嶺上是「少一張、多一張」,跟認錯一張長得一樣,要連讀三次才算,所以走不到。
更糟的是中間讀到少一張的畫面時,會被當成打牌:自己多一手,之後全部對不上。現在看**不見的那張是不
是自己碰過的牌**,是的話就是加槓,不必等。只少一張時先等,可能真的把第四張打掉了,河裡多一張才
算打牌。自己連續加槓那份素材 12 手全部排到(原本 8 手),三次加槓一次暗槓都對。

**認錯一張舊牌。** 6 索認成 3 索,之後認對時差一張。原本只有「剛摸的那張」救得回來,其他的那次打
牌被拒收,自己少一手,從此每一手都解釋不了,卡到局尾。現在動作對得上、只差一張就地改回去,連配牌
一起改。連續兩副手牌都解釋不了時放寬到三張,不會永遠卡住。

**13 張換一張。** 原本連讀三次就當成摸打,一張認錯會變成自己多打一手。但 CPU 打出去馬上被鳴走時
也長這樣,全當認錯的話 A、B 份各少一手。分得開:被鳴走時別家的副露會多一組。補上這個證據後 A 份
回到原本的數字,B 份仍少一手(線上 78 → 77、局末 84 → 83),這一手拿去換不會多打一手。

「鳴牌一致」是拿局末完整的事件流算的,線上一致又只算自己摸牌那一刻,所以**別家打牌的當下**
一直沒有數字。這裡在每張牌第一次進事件流的那一輪,把當時的事件流餵給 Mortal,再比封包:

| 問到之後建議相同 | 20/20 | 108/109 |
| 其中 Mortal 說要鳴或和 | 5/5 | 27/34 |

四份是真人、半莊、A、B。問不到的 9 次都在素材裡的半莊、A、B:三次是當場榮和,局馬上結束,
牌還沒排進來(錄的時候是立刻按的,實戰會等你按,應該只是晚,這點沒有實測);其他六次沒有逐一查。

|---|---|---|---|---|
| 改之前 | 10 | 3 | 4 | 3 |
| 改之後 | 14 | 3 | 3 | 0 |

**這個改動踩出一個舊洞:牌山 70 張。** 暫時的摸牌讓事件流出現第 71 次摸牌,引擎報錯,而報錯一次

份,**每一輪組出來、內容有變的事件流都餵進引擎**,12 份素材共 2173 個版本,報錯 0。

##### 延遲

開著 MIA 實打,建議要十秒左右才出現。逐段量過,每一段本身都不慢,差別在全螢幕時遊戲在前景,
MIA 是背景 App,macOS 會節流(App Nap)。背景 45 秒之後,100 毫秒的計時器變 300 毫秒
(`QTimer` 與 `Event.wait` 都是),認手牌變 3.29 秒。擷取跟著掉到每秒 3 幀,讀手牌時又整段
卡住,牌桌、引擎、畫面更新也各慢三倍。十秒是這些疊起來的量級,沒有直接量到。

啟動時宣告活動(`mia/utils/appnap.py`)之後,背景 100 秒計時器仍是 100 毫秒。其他段也壓過:

| 段落 | 原本 | 現在 |
|---|---|---|
| 認手牌 | 0.8 秒 | 0.2 秒,沒變的格子不重認,實測中位 0.11 秒 |
| 手牌到牌桌 | 最多等 1 秒 | 手牌在等就馬上讀 |
| 事件流到引擎 | 每 0.1 秒看一次 | 有新的馬上叫醒 |
| 建議到畫面 | 每 0.1 秒 | 每 0.033 秒 |
| 副露牌面 | 1.3 ~ 7.5 秒 | 中位 0.44 秒,最久 1.6 秒 |
| 別家打牌到吃碰建議 | 最久等 4 秒 | 最久等 2 秒,20 次有 14 次當輪就有 |

組事件流不到 1 毫秒,餵 Mortal 整局重播最久 0.16 秒。摸牌到建議估計 0.5 秒左右,手牌裡有
認不好的牌時多等一秒。這是分段加總,**還沒在全螢幕對局裡實測過**。別家打牌要等牌桌讀到,
最多一秒。

#### 5. `Hora` / `Ryukyoku`(不需要)

見 §4.4。Mortal 不看,結算畫面不必讀。

#### 6. 動畫遮擋(已知,已經有防線)

立直/和了的立繪會整個蓋住牌河。角色的皮膚色是「亮、不飽和」,與牌面的判斷
條件一模一樣,所以動畫會被讀成一排牌。

實測 1012 條牌河裡 160 條(15.8%)受影響,而**連續性檢查正確擋下了它們** ——
那道閘在做對的事。對事件流而言:那些幀直接跳過,不要試圖從中讀出捨牌。
影響的是延遲,不是正確性。

#### 7. `tracker` 層(最大的一塊新工程)

把逐幀觀察拼成事件流,並做規則校驗。**沒有舊程式可以撿**(原本那層是空的)。
它要負責的至少有:

* 去抖:同一個狀態連續出現幾幀才算數。
* 補序:一幀之間發生不只一件事時,用規則推出順序(打牌必定輪流、鳴牌必定
  緊接在某人打牌之後)。
* 棄權的處理:讀不出來的那張**延後**,不是放棄 —— 牌還在桌上。
* 規則校驗:一種牌最多 4 張、捨牌必定來自手牌、張數必定合法。
  **校驗失敗時要能說出來**,而不是送一個壞狀態給下游。

**本場、供託、場風沒有上限。** 模板只收得到打過的東西,而 9 本場、西入、北入錄不到素材。
遊戲資源裡有字形(`chang.png` 有西、北,`number` 圖集有 0 ~ 9),但透視與縮放之後對真實畫面只有
0.73,數字彼此也分不清(真的 1 對合成的 2 有 0.78),拿來當模板只是把「讀不到」換成「讀錯」。
所以不靠模板,靠規則(`RoundWatcher`、`Hud.with_sticks`):

* 本場只有兩種可能:閒家和牌歸零,其他結果都是上一局加一。讀不到就加一,讀到別的數字就是看錯。
* 供託 = (100000 − 四家點數)÷ 1000。
* 局數變小就是換場風。
* 場風讀不到不再讓事件流變空:`compose` 原本遇到 `None` 就回空,西入整局沒有建議。

真實 50 局依序驗證:本場模板只留 0、供託照樣算、場風模板全拿掉,局名本場全對。

真的打進西入靠友人場的高級設置:1 位必要點數設 200000、關掉擊飛(`--overtime`)。西字模板就是
從這樣打出來的畫面做的(正解 0.99 以上,別的字 0.77 以下)。這份規則打到西四局就結束,**沒有打到
北場**,北字沒有模板,靠上面的規則推。

關掉擊飛又抓到一個:點數可以是負的。負號讀不出來,兩家負分時過不了檢查碼,整局沒有事件流。
負號比數字矮得多,量高度就分得出來,不必有模板,21 局 8 局有負分全部讀對。

`tools/build_river_faces.py` 把每種牌平均成第二份模板,比對時取分數高的那份,素材還在,所以不會比
原本差:

### 第三輪:事件流不中斷、讀得更準、更快

先量時間花在哪。運算不到 100 毫秒(手牌 58、牌桌一輪 21、引擎幾毫秒),**摸牌到建議的 0.74 秒
幾乎都在等畫面靜止**。摸到的牌封包之後 0.22 秒就認得出來,讀牌卻要等整個手牌區停下來。牌河也
一樣:每格只認一次,而認的時機是一秒一次的碰運氣。

#### 牌河的讀錯是時機問題

同一批牌在打出後不同時間去讀(三場 2500 張,四家):

| 打出後 | 對 | 有信心的錯 |
|---|---|---|
| 0.3 秒 | 12% | 113 張(幾乎都是白) |
| 0.5 秒 | 91% | 11 張 |
| 1.0 秒 | 96% | 6 張 |
| 2.5 秒 | 98%(扣掉自己第三列 99.65%) | 4 張 |

**模板沒有問題,問題是讀在動畫中途,而且只讀一次。** 所以:

* 每 0.15 秒看一次河(6 毫秒:攤平、判有無),新格子連續兩次像素相近才算停穩。比一秒讀一次快,
  也不會讀到飛行中的牌。別家 1142 張 99.7% 對,中位 0.62 秒,之前是 96%、1.1 秒。
* 別家的牌一看就有把握、又不是白的就先收,0.48 秒,正確率一樣,之後停穩再讀一次。途中會讀錯的
  幾乎都是白。自己的牌飛得慢,牌面手牌也知道,不必搶。
* 輪到自己時沒停穩的牌也要先讀,停穩後重讀,不同就改掉(`TableWorker._revisit`)。
* 同一格的像素沒變就不重認。河被蓋住或鳴牌之後不必再花 300 毫秒認一家,之前最久一輪 0.5 秒。

#### 模板尺寸:三個地方都是同一個錯

都不是模板不好,是尺寸不對,分數掉下來就過不了門檻:

| 哪裡 | 之前 | 改成 | 結果 |
|---|---|---|---|
| 自己河第三列(靜止) | 64 x 92,七成 | 66 x 78 | 140/149 |
| 宣言牌,對家 | 共用 99 x 59,4/11 | 88 x 63 | 9/11 |
| 宣言牌,上家 | 共用 110 x 59,7/13 | 92 x 55 | 10/13 |

宣言牌要等點數才知道誰立直,那一兩秒牌面只有直放模板的雜訊。沒把握的格子順便比旋轉模板,分數
高就當猜測:39 張宣言牌的猜測 1 → 34 張對,沒把握的普通牌 37 張沒有改錯。只當猜測,不算立直,
假立直的代價太大。自己的橫放牌也不再算立直:實測手上的牌被當成立直,Mortal 之後只回摸切。

#### 快:先篩再比

完整比對絕大多數時間花在明顯不是的牌上。先用縮小一半的灰階圖挑出前六種,再做完整比對:牌河
600 格、手牌 1954 張,答案、分數、差距完全相同。一格 27 → 7 毫秒,一手 206 → 56 毫秒。

摸牌不等靜止:另外十三張沒動,只有摸牌格在動時,第一次有把握就交出去。三場 687 次沒有在動畫中途
認錯過,半透明的牌分數過不了門檻。

自己打的牌與鳴牌不等河:手牌一變就告訴排序器。排序照輪替,自己的牌飛得最慢,沒排出來的話下家、
對家的牌全部排在後面。余牌每次看河都讀,不必等整輪:太舊的話打牌的人自己那次摸牌還沒算進去,看
起來像鳴牌,要等副露確認。

#### 事件流不能停到局尾

之前一種一種補,沒補到的那種就停到局尾。現在有通用的保險:

* **停住 3 秒,用畫面重寫自己的動作**(`stream.resynced`)。Mortal 要的是現在的局面,所以配牌
  換成推回去的手牌,之前每一手當成摸切。摸切標記失真,其他都對。
* **一次看到一大批牌不再放棄整局**,照輪替補上(`TurnTracker.jump`)。中途才打開也有建議。
* **引擎報錯不等下一局**:流改掉了就救回來重播;錯的那段沒變就不救,救了只會再崩潰。
* 起始點數不是 25000 的友人場:第一局四家點數相同,總點數從那裡算。只有四家完全相同才算,
  一位數讀錯湊不出來,檢查碼的本事不打折。
* 立直後暗槓:嶺上自動摸切一秒不到,手牌從 14 張直接變 10 張,現在解釋得了。
* 別家沒有翻寶牌的暗槓不收:那是副露長度讀錯,實測憑空多出四張北。
* 河裡有把握的牌與副露牌面湊不成一組時聽河的:牌面小而且斜,河 99.7%。
* 立直的白光掃過自己的河會多讀出一張:上家打過牌才可能輪到自己,沒輪到就不補摸切;河裡消失、
  又沒有人鳴牌的那張不算打過。這是之前「50 局 1 局」的那個問題,實測一局因此 40 手沒有建議。
* 宣言牌比一格寬,點數一變,標記常落在多讀出來的那一格:旋轉模板比較像的那格才是宣言牌。
* 和了之後的結算畫面會一次讀出一排假牌:整批補上要余牌也跟著減。
* 副露長度至少隔 0.4 秒量一次。牌桌現在有牌落下就走一輪,隔太近的話「連讀兩次一樣」兩次都讀到
  鳴牌動畫的過渡值。

#### 實打:滑鼠滑過手牌時停不下來

重播的摸牌到建議是 0.37 秒,實打第一場卻還是 0.73 秒,分布分成兩群:三成在 0.3 秒內,其餘落在
0.6 ~ 1.3 秒,也就是「一直沒停,滿 15 幀才強制讀」。實打中直接擷取量:手上有摸牌時相鄰兩幀只有
一成完全相同,變化是滑鼠滑過手牌(經過的牌會抬起來)與摸牌那格的動畫。錄影只存變化夠大的幀,
這些都被濾掉,所以重播看不到。

所以手牌區動的時候也看一眼,只重認變了的那幾格(快篩之後一格約 4 毫秒):另外十三張認出來與停下

四個改動:

#### 量錯過一次:不是 GIL

鳴牌之後 4 秒內的別家捨牌,一半以上晚 1 秒以上,離鳴牌遠的只有 4~7%。第一個猜測是認牌面那條執行
緒搶 GIL,做了一個對照:主執行緒讀牌河,旁邊同時認副露,慢了一百倍。改成另開行程之後才發現,對照
組那一幀那家根本沒有副露,函式立刻返回,旁邊是空轉的迴圈在搶 GIL。換成真的副露重量:執行緒 0.71 →
0.73 秒,行程一樣。所以留著執行緒。

真正的原因有兩個:

* **鳴牌的人打的牌要等副露確認。** 確認要隔 0.4 秒再量到一樣的長度,實測那張牌讀到之後還要再等
  0.7 秒,後面兩家的牌排在它之後,也跟著晚。現在三個證據都有就先排進去:打之前余牌沒減(沒人
  摸牌)、余牌讀過、他的副露區已經量到長了一組吃碰(像槓的不算)。結算畫面的假牌只滿足第一個。
  之後的確認由「先記帳」抵掉,不會鳴兩次。重播同一局,下家吃那張從 63.56 秒提早到 62.84 秒。
* **「整局都慢」其實是漏牌。** 延遲照「這家第幾張」對,事件流少了一張,後面每張都晚一整圈。這是
  準確率的問題,不是延遲,報告的 p90 被它灌高了。

### 摸切與手切

之前畫面那條路的別家捨牌一律填手切,而素材裡別家自己決定的捨牌 59% 是摸切,等於只對 41%。Mortal
拿摸切、手切判斷別家的手有沒有在變,這一欄錯了它看到的別家就不對。

#### 牌河上看不出來,要看手牌

摸切與手切的牌在牌河裡畫得一樣(局尾比對過,亮度、樣子都沒有差別)。看得出差別的是打牌那一刻的
手牌:別家的手牌是一排橘色牌背,摸到的那張隔一點空放在尾端。摸切時尾端那張直接不見;手切時中間
空出一格(或一端短一截),尾端那張還在,約一秒後才滑進去補。

三家的量法不一樣(`mia/vision/tiles/backs.py`):

* **對家、上家沿著手牌畫一條線**,量線上哪裡有牌背。「摸到的那張還隔開著、本體卻比原本短」就是
  手切的樣子。打牌時角色的手會伸過手牌,把它切成好幾段,這種幀不算。
* **下家數橘色區塊**。下家在畫面右側,遠端被透視壓扁,沿線量的話空出來的那格只剩幾個像素,而且
  手會整條橫過手牌。牌背膨脹一點,同一段就連成一塊:手切時分成兩塊、總面積幾乎不少;被手蓋住時
  總面積少一大截。

量測一律換算成牌桌寬 2560 像素的單位。三家一次約 3 毫秒,每次看河都量。

**量之前先把顏色降成一半解析度。** 上面的門檻都是在錄影上調的,錄影存成 JPEG,顏色只有一半解析度
(4:2:0)。實打拿到的是原始畫面,牌與牌之間那條淡色的細縫清楚得多:上家沿線量到的接縫掉到門檻
以下,最後一張手牌被切開、當成隔開放的摸牌,每一次量都是「摸牌隔開、本體短一張」。2026-11-09
CPU 場實打,上家摸切與手切只對 42% ~ 57%,同一場錄影重播卻是 100%;同一張原始畫面原圖與 JPEG
各量一次,上家 1726 次有 1320 次不同。所以量之前照 JPEG 的做法把顏色降成一半解析度、亮度不動
(`_like_jpeg`):原始畫面量出來與 JPEG 一致,錄影再降一次幾乎不變(四份錄影重播,三家的摸切
只有變好或持平)。三家一次約 4 毫秒。

#### 每場重播兩次,兩次都錯的才修

同一份程式重播兩次結果會不一樣(時機差一點,排序就走另一條路),所以每場跑兩次,只追兩次都出現的錯:

* **叫牌提示的光框。** 自己能鳴的那張牌被框上一圈淡綠色的光,光溢到下一格,下一格的亮度中位 112
  剛好過門檻 110,被當成一張讀不出來的新牌。接著那張被鳴走,河又短回去,這張假牌佔掉了那家下一張
  真捨牌的位置:東三局對家的 9 索從事件流裡消失,兩次都是。光框那一格的亮像素八成是淡綠色,但亮的
  只佔兩成;牌面的亮像素是象牙色,一場九萬多格 99.9% 在 0.32 以下(`river._call_glow`)。
* **寬的宣言牌被鳴走。** 橫放的宣言牌被讀成兩格讀不出來的牌,下家想了 5 秒才碰,河一次少兩格,
  `RiverWatcher` 只認少一張,於是上家下一張 6 索被當成「2 萬被鳴走」吞掉。尾端兩格以上全是讀不出來
  的牌不見了,看到兩次(或之後的河接在剪掉的那條後面長出來)就剪掉(`RiverWatcher._trim`)。碰的牌面
  與宣言牌從此對了;宣言牌被鳴走後,下一張捨牌照規則也要橫放,那一張還讀不對。
* **加槓的嶺上。** 燈那條路摸打只加一張,加槓的嶺上讓余牌多減的那張沒吸收,之後上家吃牌(沒摸)看起來
  像摸打。改成與余牌那條路一樣吸收。
* **局尾重寫配牌。** 事件流在局尾本來就不會再動,停住 3 秒後結算畫面上還讀得到手牌,`resynced` 拿它
  倒推,配牌整副換成局尾的手牌,之後每一張摸牌都錯(電腦場東四局 14 個問題,13 個是這個)。打牌時
  的建議沒受影響,但事件流 Log 與報告都是錯的。重寫出來的配牌與原本差超過 3 張就不採用:中途漏記
  一兩手只差一兩張。
* **晚到的吃。** 電腦一打出就吃,吃的人的牌比再下一家的牌晚讀到。`_restore_turn` 把它換回輪到的位置時
  一律當成摸過牌,吃就被排成摸打,整組不見。他的副露區正在長、或已經多了一組時不這樣改。
* **燈分不出下家吃與摸。** 兩者都是燈直接換到下家。第一版只要副露區沒在長就當成摸打,電腦一打出就吃、
  副露還沒開始長的那一下就被排成摸打(170335 東一局,每次重播都漏那一組吃)。改成比兩個余牌讀數:
  燈換到 ``last`` 之後讀到的第一個,與換到下家之後讀到的第一個,少一張才是摸。兩個都在換手之後讀的,
  不受算出來的張數影響,東二局那種多算一張的情況照樣救得回來。

* **手底下的假牌。** 打牌時角色的手伸過自己的河,膚色跟牌面一樣亮又不橘(色相 9 ~ 12、飽和度 24 ~ 29;
  牌面是 30 與 2),手底下多出一兩格讀不出來的牌,手收回去就沒了。`RiverWatcher.thrown` 照樣算了它,
  於是局尾「河裡比手牌多一張」補出一次不存在的摸切 4 筒,4 筒張數一超過,對家讀對的 4 筒就被當成讀錯
  換成東,上家吃那組跟著錯(真人東三局 1 本場的 3 個錯全是這一張)。在畫面上擋膚色不行:沒被手蓋住的
  真牌(紅色的萬子)膚色比例也到 0.49。改成記下「還沒讀出來就不見」的格子(`unread_gone`),自己打過
  幾張扣掉它們;別家鳴走一張沒讀出來的自己的牌時會少算,那只會讓補摸切晚一點。

已知但沒修的:局尾最後一兩手來不及排(和了 0.4 秒前打的牌);宣言牌被鳴走後的下一張橫放牌。

### 副露:先列候選,再到畫面上比

舊的做法(`read_meld_faces`)從畫面**認牌**:掃整段帶子,每一框問「這是 37 種牌的哪一種」,認不全就照
剩幾張猜。但看副露之前,大部分答案已經知道了:被鳴的牌是河裡剛少掉的那張(有把握的 99.7% 對),
從誰那裡鳴的排序器知道,吃碰還是槓看長度。剩下的只有幾種可能,所以改問「這組是 A 還是 B」
(`mia/vision/tiles/meld_fit.py`):

* **候選。** 碰一種;從上家鳴的數牌再加最多三種吃(被鳴的那張在順子的低、中、高),張數湊不出來的
  不列(`_Composer._looked`)。從對家、下家鳴的只能碰,牌由被鳴的那張決定,畫面只用來看赤五。
* **排法。** 雀魂的橫放牌:上家的放最左、對家的放中間、下家的放最右;吃一定是上家的,排成
  [被吃的, 小, 大]。橫放牌寬約 1.4 倍。八組逐張對過,全部符合。
* **比。** 照每個候選的排法,把該在每一格的那張牌的模板拿去比,整組一起挪、一起縮放、上下移,分數
  加起來最高的那個,贏第二名 0.05 以上才採用。2026-11-03 的整合複驗又補上畫面品質門檻,
  見下節;光是贏過其他候選不足以採信。

先試過「照橫放位置切框、逐張認」:位置給對了,認得出來的也只有 58%,框偏一點就認不出來,從部分牌面
補齊整組又把錯放大(49 組錯 4 組)。比候選不必每張都認清楚,差的那一兩張分數拉得開就夠了。

**座標不用帶子的格子。** 帶子的角點是為了量長度搜的,一格不等於一張牌,上一組量到的結尾也會偏(真人
那場下家第二組,落在 4 萬正中間)。量得準的只有最新那端的邊,從那裡在牌河的攤平平面上往內排。對家

**赤五在對到的牌面上量。** 排好之後每張牌在哪就知道了,把那一格模板對到的牌面切下來問紅墨比例。

|---|---|---|---|

#### 辨識流程加速與赤五修正(2026-11-04)

* **副露只比可能出現的區域。** 模板比對占副露候選計算約九成,原本每一種牌在整組影像上都比一次,

#### 染成淡藍的赤五(2026-11-08)

七份錄影別家打出赤五 30 次,讀成普通五 2 次,都是對家:053001 西一局的赤五萬、155238 東三局的

那兩幀整張牌被染成淡藍。滑鼠停在手牌某張牌上時,河裡同種的牌會染色提示,自動打牌選牌時也一樣。

修法是白平衡(`classify._untint`):牌面最亮的四分之一當紙色,飽和度在 45 ~ 110 之間、亮度高於
170 就算染過色,各色版乘上「220 / 紙色」再量。只看最亮的四分之一,是因為萬子字多,整張的中位數
被墨水拉到 167。桌布 140 / 150、牌背飽和度 169,都不會被當成染色的紙;沒染色的牌一個像素都不動,

### 5.1 為什麼要一支重播工具

`tools/eval_rivers.py` 量的是「**讀圖的函式**對不對」:它自己挑動畫演完的
幀、每幀從頭認、開多行程衝吞吐量。app 裡那條 1 Hz 的迴圈不是這樣跑的 ——
`tools/replay_table.py` 把同一份錄影餵進真正的 `TableWorker`,量「**跑起來**
對不對」。差別有四件,而每一件都是離線評測結構上看不到的:

| | 離線評測 | 實際那條迴圈 |
|---|---|---|
| 挑哪一幀 | 自己跳過轉場 | 拿當下最新那張,**不重試** |
| 認幾格 | 每幀全部 | 只認新增的,**錯誤會累積** |
| 行程 | 多行程 | 單行程,要量「一輪來不來得及」 |
| 比什麼 | 讀出來的牌 | tracker 的狀態 |

**它第一次跑就抓到一個無症狀的 bug。** `RiverWatcher._drop_one` 把「某一輪
少讀到一格」當成鳴牌,整排往前挪一位,回來的那張於是被當成新捨牌 ——
放銃分析的河裡多出一張**假現物**(說「一定安全」的牌)。而同一輪的格線是
**0% 錯**:認牌全對,錯在兩次觀察之間怎麼解讀差異。

#### 兩把尺

拿錯會得到一份看起來很正常的假報告:

* 比**格線**(認得對不對)→ `visible_river`,被鳴走的牌畫面上真的不在了
* 比**tracker**(放銃分析吃什麼)→ `river`,振聽看的是「他打過」

這裡踩過一次:第一版拿 `visible_river` 當 tracker 的答案,量到 4.98% 的
假現物,而幾乎全部是被鳴走的牌 —— tracker 留著是對的。`eval/rivers.py` 的
模組說明警告過反過來的那一半。

#### 現在的數字(20261024-123746,447 輪)

```
格線      對 65.5%   棄權 34.5%   錯 0.0%   漏格 0
tracker   真現物 844   假現物 0 (0.00%)
事件      立直 2/2   寶牌 4   局邊界 4   鳴牌 5
診斷      看不懂 1(另有 7 次是河整個空掉)   先不動 13
延遲      中位 12ms   p95 214ms   最久 473ms   超出 1 秒預算 0 輪
```

最後一行是離線評測量不出來的:**1 Hz 綽綽有餘。**

那剩下的「看不懂 1」查過了,是自己那家被遮住而其他三家都滿的那一幀 ——
watcher 拒絕解讀,所以沒有損害。但它指出一個**還沒用到的證據**:四家的河
不會同時只有一家崩掉。跨家的一致性檢查目前完全沒做,`read_river` 與
`RiverWatcher` 都是逐家獨立的。

## 六、怎麼知道做到了

素材已經有了:`data/recordings/20260801-110639` 有 3036 幀,

建議的驗收標準:

## 七、沒有副露時要講明白

在第 6 步完成之前,放銃分析會少算「壁」的張數與「3副露」這個威脅標籤。
**兩者都是低估威脅的方向** —— 也就是會把危險牌說成比較安全。

這件事必須在 UI 上講明白,不能默默少算。這是這個專案一貫的原則:
少算要讓人知道,因為它錯的方向是危險的那邊。
