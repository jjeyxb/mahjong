# 混合辨識（樣板＋YOLO）

在任一功能頁的「設定 → 畫面辨識方式」選擇 **混合辨識（樣板＋YOLO）**。三個功能頁的選單會沿用既有同步機制，一處改選，其餘兩處同步，並保存至下次啟動。已開啟的 MIA 需重新啟動以載入新選項。

網頁版的 AI 建議若要走混合辨識，仍需在 AI 建議頁勾選「使用圖像辨識」；放銃分析可用既有的「強制使用圖像辨識」選項。封包來源不受辨識後端選擇影響。

## 為什麼要混合

兩個後端錯的地方幾乎不重疊（七份錄影，2026-11-08）：

| | 樣板 | YOLO |
|---|---|---|
| 自己的回合排得到 | 705 / 705 | 698 / 705 |
| 引擎報錯（拒收事件流） | 0 | 11 |
| 別家捨牌讀錯 / 多讀 | 14 | 0 |
| 自己摸牌到看得到（中位） | 0.29 秒 | 0.49 秒（沒算推論時間） |

樣板讀自己又快又穩，弱點是別家：偶爾一張牌讀錯、多讀一張，或讀出假的吃碰，那一局之後的建議全跟著錯。YOLO 讀別家幾乎不錯，弱點是自己的手牌與摸牌，而且比樣板慢。

## 運作方式

```text
同一張已校正的畫面
  ├→ 樣板：手牌、牌河、副露 → TableWorker → 完整的事件流
  └→ YOLO：1920×1080 推論 → LedgerStream → 完整的事件流
         → StreamMerger 在事件層合併 → 建議、放銃分析
```

兩條路各自是原本的樣板與 YOLO，沒有改動；合併在 `src/mia/hybrid/merge.py`。以樣板為主幹，YOLO 追上之後拿來核對別家：

1. 兩條事件流逐事件對齊（`difflib.SequenceMatcher`）。一致的段落照用。別家的摸牌看不到牌面，對齊時綁上它後面那個事件，否則錯位的兩段會到處「對上」；摸切與否不比。對齊之前，立直成立排回宣言牌正後面（封包裡一定是這個順序），宣言牌還沒讀到的先拿掉：YOLO 有時把立直成立排在下一家摸牌之後，也有時立直棒先讀到、宣言牌還沒有。
2. 夾在兩個一致點之間、不一致的一段，整段挑一邊。一致點上兩邊局面相同，整段換掉仍然合法。
   - **有自己動作的段落用樣板。** 自己的手牌樣板讀得準，YOLO 讀錯會讓引擎拒收。別家鳴自己打的牌不算自己的動作。
   - **別家的段落用 YOLO**，除非 YOLO 在那一段落後超過 2.5 秒（`LAG_OK`）：那是 YOLO 卡住、整局錯位。
   - **樣板有吃碰或立直成立、YOLO 整段什麼都沒有，用樣板。** 被立刻鳴走的牌只在河裡停一下，YOLO 要牌停穩才收，捨牌、鳴牌、鳴後打的那張整段都不在；樣板的假吃碰則是 YOLO 在同一個位置看到那家照常摸打。立直成立也是，立直棒放上桌之前 YOLO 不送。
3. 最後一個一致點之後用樣板。YOLO 還沒追上就不等它，建議的速度由樣板決定。
4. 拼起來不合理的（暗槓之後、下一張捨牌之前沒翻寶牌，或同一種牌看得見超過 4 張），一段一段換，換了會不合理的那段退回樣板。
5. 換局時樣板還沒讀到開局資訊，先用 YOLO 的；YOLO 還停在上一局的話不用。

「停住」「等手牌」這類狀態跟著樣板。局數由合併層自己數，兩個後端各數各的。

舊版（2026-11-06，commit 10791cf）在 YOLO 的定位上逐張用樣板核對牌面，自己和別家都由 YOLO 的事件流決定，結果跟純 YOLO 幾乎一樣，已經移除。

## 驗證

### 離線，兩條現成的事件流重新合併

七份錄影、705 個自己的回合，建議與封包相同：

| | 第一次排到時 | 出牌那一刻 | 引擎報錯 |
|---|---|---|---|
| 樣板 | 697 | 686 | 0 |
| YOLO | 688 | 645 | 11 |
| 合併 | 702 | 692 | 0 |
| 合併，YOLO 再慢 1 秒 | 701 | 690 | 0 |

「出牌那一刻」取封包裡下一個事件發生前、最新的事件流，就是玩家實際看得到的建議。705 是上限：剩下的錯在 053001 一次樣板讀出的假吃（自己的段落，照規則用樣板），以及幾次快手玩家打得比樣板讀得還快。

### 即時，真的跑 YOLO 推論

`tools/selfplay.py replay <錄影> --vision hybrid` 把錄影照原時間餵進混合辨識，兩個後端與 YOLO 推論同時在跑（MPS）。

七份錄影、705 個自己的回合、2920 張捨牌。三條事件流出自同一次重播：

| | 建議相同：第一次排到時 | 出牌那一刻 | 鳴牌判斷相同 | 引擎報錯 | 捨牌 錯 / 漏 / 多 | 假副露 |
|---|---|---|---|---|---|---|
| 樣板 | 693 | 683 | 249 / 264 | 0 | 7 / 7 / 9 | 2 |
| YOLO | 644 | 263 | 96 / 264 | 37 | 2 / 59 / 0 | 0 |
| 合併 | 697 | 687 | 253 / 264 | 0 | 1 / 6 / 3 | 0 |

決策點從封包發生到事件流排到的時間（中位 / p90）：

| | 自己摸牌 | 別家捨牌 |
|---|---|---|
| 只跑樣板 | 0.31 / 0.83 秒 | 0.73 / 1.04 秒 |
| 混合裡的樣板 | 0.31 / 0.79 秒 | 0.72 / 1.11 秒 |
| 混合裡的 YOLO | 1.66 / 3.73 秒 | 2.09 / 3.16 秒 |
| 合併 | 0.31 / 0.79 秒 | 0.72 / 1.11 秒 |

YOLO 實際推論比樣板晚 1 秒多，selfplay 打得快，常常牌都打出去了 YOLO 還沒看到摸牌，所以單獨用 YOLO「出牌那一刻」只有 263。合併不等 YOLO，速度與樣板相同，YOLO 追上之後再改正別家。

合併的數字是把這次重播記下的兩條原始事件流（`raw_template`、`raw_yolo`，帶著原本的時間）用最終版的規則重新合併；重播時跑的是前一版規則（第一次 695、出牌那一刻 686）。

剩下與封包不同的建議：

- 053001 西二局三本場 4 次：樣板把自己吃上家 2p 讀晚一圈，之後自己的摸打全部錯開一格。YOLO 這局讀對了，但自己的段落用樣板（整體 YOLO 自己的摸牌錯得比樣板多，自摸錯 22 對 5）。根源在樣板的吃牌時序。
- 053001 東三局一本場 1 次：樣板與 YOLO 都錯。
- 053001 西一局一本場 1 次：YOLO 把上家一張 8p 讀成 E，合併採用了。同一局 YOLO 也改正了樣板把 W 讀成 F 的錯。這是信 YOLO 讀別家的代價。

另有 12 個回合在出牌前樣板還沒排到（快手玩家打得比樣板讀得快），合併也一樣。

評分記錄的「自摸錯」有幾次不是讀錯：莊家開局畫面上一次 14 張，兩個後端都把最右邊那張當成摸牌。牌是同一組，建議不受影響。

## 速度與資源

建議的速度跟樣板一樣：合併只在 YOLO 追上的部分改寫，沒追上的不等。在這台 Mac（MPS）上同時跑 YOLO 推論沒有讓樣板變慢（見上表）；只在錄影重播量過，真人對局的實機負載還沒量。CPU 與 GPU 的負載是兩個後端相加；在沒有 GPU 的機器上 YOLO 會更慢，那時合併層多半直接用樣板（YOLO 落後超過 2.5 秒的段落不採用）。
