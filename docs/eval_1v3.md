# 1v3 評測紀錄

每一份風格權重對上三個**未微調的** `mortal_298k`,量它的平均順位。
這份檔案只記「跑了什麼、得到什麼、為什麼這樣讀」—— 方法與結論的來龍去脈在
`handoff.md` 的「M8」那幾節。

> 最後更新 2026-09-30。

---

## 設計

```
challenger = 要測的風格權重  ×1
champion   = models/mortal_298k.pth  ×3
seed_key   = 20260929
```

**三個對手是同一份未微調的權重,不是三個不同模型。** 要問的是「微調之後對上
原本的自己,還打得一樣好嗎」,所以對照組必須是同一個模型的未微調版本。

`libriichi::arena::OneVsThree` 的座位安排:每一個種子打 **4 次半莊**,
challenger 分別坐 0/1/2/3,champion 補其餘三家。

```
split A   [測試, 標準, 標準, 標準]
split B   [標準, 測試, 標準, 標準]
split C   [標準, 標準, 測試, 標準]
split D   [標準, 標準, 標準, 測試]
```

所以 `seeds_per_iter = games_per_iter // 4`,起家的優劣被消掉。

`seed_key` 固定成 20260929,所有權重打**完全相同的牌山與配牌** —— 比較是配對
的,牌運從差異裡消掉。這是整個評測最重要的一行設定。預設值 `-1` 會用
`secrets.randbits(64)` 隨機產生,那樣每份打不同牌局,3,000 場的差異會被牌運淹掉。

### `mortal_298k` 自己不必跑

它當 challenger 時對手是三個它自己,四家同一個模型、而且輪坐四個座位 ——
平均順位**依定義**是 2.500,不是量出來的。它是那把尺,不是被量的東西。

## 結果

### 15,000 場(2026-09-30)

| 權重 | 場數 | 平均順位 | SE | 離 2.500 |
|---|---|---|---|---|
| `style_call_high`(愛鳴牌) | 15,000 | **2.4838** | 0.0091 | −0.0162 = 1.78σ |
| `style_call_low`(不愛鳴牌) | 15,000 | **2.5065** | 0.0090 | +0.0065 = 0.73σ |
| `style_reach_high`(愛立直) | 進行中 | | | |
| `style_reach_low`(不愛立直) | 進行中 | | | |
| `mortal_298k`(標準) | — | 2.500 | — | 依定義 |

每輪的平均順位:

| 權重 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| `call_high` | 2.5080 | 2.4780 | 2.4663 | 2.4740 | 2.4927 |
| `call_low` | 2.5103 | 2.5210 | 2.5017 | 2.4883 | 2.5113 |

| 權重 | 95% CI | 平均 pt | 名次分布(均等應各 3,750) |
|---|---|---|---|
| `call_high` | [2.4659, 2.5017] | +1.071 | `[3781, 3874, 3652, 3693]` |
| `call_low` | [2.4889, 2.5241] | +0.564 | `[3579, 3851, 3963, 3607]` |

兩份的名次分布正好相反:`call_high` 是**一二位都多、三位最少**,
`call_low` 是**一位最少、三位最多**。

#### 副露率兩端的差距

```
call_low 2.5065 − call_high 2.4838 = +0.0227  =  1.78σ
```

方向是「愛鳴牌比較好」,但**沒過 2σ**,而且兩個 95% CI 還有重疊。三個數字
(high 偏低、low 偏高、兩端差 1.78σ)一致指向同一個方向,比純雜訊該有的樣子
整齊 —— 但不足以下結論。要推過去得再加場數。

## ⚠ 3,000 場不足以比順位

`style_call_high` 從 3,000 場加到 15,000 場,結論**翻了方向**:

```
3,000 場   2.5080   → 「比基準差一點」
15,000 場  2.4838   → 「比基準好一點」
```

而 2.5080 正是那五塊裡最高的一塊。它不是量錯,是運氣 —— 單塊 3,000 場的標準誤
是 0.020,跟想量的效應同一個量級,第一塊落在哪邊幾乎是擲骰子。

**要比順位就得先算需要多少場。** SE 隨 `1/√n` 縮,以 2σ 為門檻:

| 想分辨的差距 | 每份場數 | 每份時間 |
|---|---|---|
| 0.020 | 15,000 | ~1.8 小時 |
| 0.010 | 50,000 | ~6 小時 |
| 0.005 | 200,000 | ~24 小時 |

(時間是機器空著、一份一份跑的實測外推。)

**這個限制只對「順位」成立。** 打法差異是 16~20σ 等級的,3,000 場綽綽有餘 ——
兩者的效應大小差了一個數量級,不要把「順位分不出來」讀成「什麼都分不出來」。

## 怎麼跑

`eval.toml` 是樣板,進版控;執行期會生 `eval_<key>.toml`(gitignore)。
一次只改三個地方:

| 改哪裡 | 值 |
|---|---|
| `[1v3.challenger].state_file` | 要測的權重 |
| `[1v3].log_dir` | 一份一個目錄,否則牌譜混在一起分不開 |
| `[1v3].iters` | 場數 = `games_per_iter × iters` |

```powershell
cd engines\mortal\Mortal\mortal
$env:MORTAL_CFG = "../../eval_call_high_15k.toml"
..\..\.venv\Scripts\python.exe -u one_vs_three.py
```

### ⚠ 改設定要認區段

`eval.toml` 裡有**兩個** `state_file`:challenger 那個指向 `style_*.pth`,
champion 指向 `mortal_298k.pth`。用前綴比對去改會把兩個一起換掉,結果是拿風格
權重當對照組 —— 而四家同一個模型的平均順位必然是 2.500,**那個數字看起來完全
正常,不會有任何錯誤訊息**。2026-09-28 在 `finetune.toml` 上真的踩過一次。

### ⚠ `iters = 1` 會重跑同一批牌局

`seed_start` 在上游寫死是 10000,每輪往前推 `seeds_per_iter` 個種子。所以
`iters = 5` 的區塊是 10000 / 10750 / 11500 / 12250 / 13000 —— **第一塊永遠是
那 3,000 場**。想加場數只能靠調大 `iters`,而且第一輪一定會重跑。

不能改(`seed_start` 在上游程式碼裡,而 `Mortal/` 是 gitignore 的 clone,
改了下次重新 clone 就沒了)。

### ⚠ 中途看不出死活

輸出重導到檔案時,Rust 那側的進度條偵測到不是終端機就自我關閉,所以每一輪
**只寫兩行**(開頭的 seed、結尾的 rankings)。「日誌沒長大」在這裡不是卡死的
證據,唯一的存活訊號是行程的 CPU 時間還在增加。

看門狗不能用「輸出檔多久沒動」—— 那對訓練有效,對評測無效。改用牆鐘上限。

### ⚠ 一輪之內不能續跑,但輪與輪之間可以

`one_vs_three.py` 是**每一輪各自建 env、各自寫牌譜、各自印 rankings**,所以
`iters > 1` 時中斷只損失當下那一輪。單一輪跑到一半中斷則是全部重來。

## 這個評測是確定性的

`one_vs_three.py` 沒有傳 `boltzmann_epsilon`(預設 0),所以引擎走
`q_out.argmax(-1)` —— 完全貪婪,沒有取樣。同樣的 `(seed, key)` 重跑會得到
**逐場相同的動作序列**。

2026-09-30 實測:`call_high_15k` 的第一輪與 2026-09-29 的 `call_high`,
3,000 份牌譜的動作序列 **3000/3000 相同**,rankings 一字不差
(`[740 728 800 732]`)。

⚠ 但**牌譜檔本身不是逐位元相同**。`meta` 裡有 `eval_time_ns`(牆鐘時間)與
`batch_size`(當下有幾局在等決策),那兩個每次都不一樣。拿整個檔案算雜湊會得到
「0/3000 相同」這個嚇人的結論 —— 要比就比去掉 `meta` 的事件序列。

## 牌譜怎麼分析

輸出是標準 mjai,`start_game.names` 直接標明誰是誰:challenger 叫 `style`、
champion 叫 `baseline`(設定裡的 `name` 欄位)。所以同一局裡的三家 baseline
是**同場對照** —— 它們打的是完全相同的牌。

`tools/style_profile.py` 的 `scan_game()` 可以直接吃。

### ⚠ 這些牌譜餵不進 MIA 自己的工具

`advise.py` 與 `tools/ui.py --replay` 會失敗:MIA 的 `StartGame` 要求 `id`
(自己坐哪),而那是**給某一家的事件流**才有的欄位;第三人稱的牌譜沒有,
解析當場失敗,接著被誤判成 WebSocket 錄影,最後只說「裡面沒有事件」——
錯誤訊息跟真正的原因一點關係都沒有。

要用得先決定「以哪一家的視角重播」並補上 `id`。
